# Hotel Project

REST API системы бронирования отелей на Spring Boot. В репозитории четыре
независимых приложения со своими зависимостями и Gradle Wrapper. Общей сборки нет.

## Архитектура

| Приложение       | Назначение                            | Порт |
|------------------|---------------------------------------|------|
| discovery-server | Реестр Eureka                         | 8761 |
| api-gateway      | Маршрутизация внешних запросов        | 8080 |
| hotel-service    | Отели, номера, занятость и статистика | 8081 |
| booking-service  | Пользователи, JWT и бронирования      | 8082 |

Gateway направляет запросы по явным маршрутам, а каждый бизнес-сервис
самостоятельно проверяет JWT и права доступа. Booking Service хранит пользователей
и бронирования в своей H2, Hotel Service — отели, номера и журнал резервирований
в другой БД. Между ними используется HTTP через Eureka и LoadBalancer.

Booking Service создает бронирование в статусе `PENDING` и запрашивает
подтверждение у Hotel Service. Если операция не удалась, бронирование отменяется,
а освобождение номера при необходимости завершает фоновый обработчик.

Пользователь может выбрать номер сам или воспользоваться автоподбором, посмотреть
историю и отменить бронирование. Администратор управляет пользователями, отелями
и номерами, просматривает статистику занятости. Автоподбор отдает предпочтение
номерам, которые бронировали реже.

## Docker Compose

Для запуска в Windows, macOS и Linux нужны Docker с Linux-контейнерами и
Compose v2. Сборка приложений, генерация ключей и подготовка учетных записей
выполняются в контейнерах. Устанавливать JDK, Gradle, Python или OpenSSL на хосте
не требуется. При первом запуске загружаются образы и зависимости из Docker Hub,
Gradle и Maven Central, поэтому время сборки зависит от скорости сети.

Из корня репозитория:

```sh
docker compose up --build
```

После сообщения `Local stack is ready` от `access` доступны четыре приложения:

| Назначение              | Адрес                                                                 |
|-------------------------|-----------------------------------------------------------------------|
| API Gateway             | http://localhost:8080/api/v1                                          |
| Eureka                  | http://localhost:8761/                                                |
| Swagger Booking Service | http://localhost:8082/swagger-ui.html                                 |
| Swagger Hotel Service   | http://localhost:8081/swagger-ui.html                                 |
| OpenAPI Booking / Hotel | http://localhost:8082/v3/api-docs / http://localhost:8081/v3/api-docs |

У каждого приложения есть `/actuator/health`. Задача `setup` готовит ключи и
конфигурацию, а `access` дожидается маршрутов Gateway, регистрирует тестового
пользователя и выпускает токены. Обе завершаются с кодом 0, после чего четыре
приложения продолжают работать. Состояние и логи доступны в другом терминале:

```sh
docker compose ps -a
docker compose logs access
docker compose logs -f booking-service hotel-service
```

Для запуска в фоне используется `docker compose up --build -d`. Сообщение о
готовности можно посмотреть через `docker compose logs access`.

Команды Compose одинаковы для PowerShell, cmd и Unix-терминала. На Windows
в Docker Desktop нужен режим Linux containers. Подготовка Docker описана в
[инструкции установки](https://docs.docker.com/desktop/setup/install/windows-install/).

### Доступы для Swagger

Ключи и случайные пароли создаются автоматически в Docker volumes. Приватный ключ
подключен к Booking Service, публичный — к обоим бизнес-сервисам. Пароль первого
ADMIN передается Spring Boot через файл `configtree`, без значения в Compose-файле
или командной строке процесса. Секретные данные не включаются в образы.

Готовые учетные данные и JWT копируются одной командой:

```sh
docker compose cp booking-service:/run/local/access/. ./secrets
```

Она создает каталог `secrets`, если его нет, и помещает в него четыре файла:

| Файл                           | Назначение                                                                    |
|--------------------------------|-------------------------------------------------------------------------------|
| compose-admin-credentials.json | Логин `hotel_admin` и случайный пароль ADMIN                                  |
| compose-user-credentials.json  | Логин `compose_guest` и случайный пароль USER                                 |
| compose-admin-token.json       | Токен для управления пользователями, отелями, номерами и просмотра статистики |
| compose-user-token.json        | Токен для поиска номеров, бронирований и личной истории                       |

Каталог `secrets/` исключен из Git. Для авторизации в Swagger в поле
`Authorize` → `userBearer` используется значение `accessToken` из нужного
файла, без префикса `Bearer`. Пароли и JWT в логи не выводятся.
Токены действуют час. Для их обновления:

```sh
docker compose run --build --rm --no-deps tools access
docker compose cp booking-service:/run/local/access/. ./secrets
```

### Проверка требований

Автоматическая проверка работающего стенда:

```sh
docker compose run --build --rm --no-deps tools check
```

Она проверяет Eureka и маршрутизацию, JWT и роли, управление пользователями,
отелями и номерами, поиск и рекомендации, явное и автоматическое бронирование,
идемпотентность, конкурирующие запросы, личную историю, отмену, статистику и
доступность Swagger. Каждый запуск создает свой отель и номера, поэтому проверку
можно повторять на заполненном стенде. Существующие бронирования сохраняются.

Сценарии с потерей ответов, гонками подтверждения/отмены, блокировками БД,
невалидными JWT, миграциями и перезапуском обработчика восстановления проверяются
существующими тестами приложений. Все четыре независимые сборки с тестами
выполняются внутри отдельного контейнера:

```sh
docker compose run --build --rm tests
```

Команда завершается с ненулевым кодом при ошибке сборки или теста. Кэш Gradle
сохраняется в отдельном volume. Для этой проверки не нужен установленный на хосте
Java или запущенный вручную стенд.

| Требование                                             | Проверка                                                     |
|--------------------------------------------------------|--------------------------------------------------------------|
| Четыре сервиса и Eureka/Gateway                        | `docker compose ps`, Eureka, `tools check`                   |
| JWT на один час, USER/ADMIN, управление пользователями | `tools check`, тесты Booking/Hotel Security и аутентификации |
| Отели и номера                                         | Swagger Hotel Service, `tools check`                         |
| Занятость по датам, рекомендации и статистика          | `tools check`, тесты Room/Reservation                        |
| Двухшаговое создание и компенсация                     | `tools check`, тесты BookingCreation и восстановления        |
| Конкуренция, идемпотентность и блокировки              | `tools check`, транзакционные тесты H2                       |
| История, владение и отмена                             | Swagger Booking Service, `tools check`                       |
| Ошибка зависимости и фоновое восстановление            | Сценарий паузы ниже и тесты восстановления                   |
| OpenAPI и валидация контрактов                         | Swagger двух сервисов и тесты OpenApiConfig                  |

Ручная проверка доступна в Swagger: под ADMIN создаются отель и номер, под USER —
бронирование. Затем доступны история, отмена и статистика ADMIN. Даты нового
бронирования начинаются не раньше текущей даты UTC и образуют непустой интервал.
Для явного выбора используется `autoSelect=false` с `roomId` без `hotelId`, для
автоматического — `autoSelect=true` с `hotelId`.

### Сбой Hotel Service и восстановление

После успешного `tools check` подготовлен свободный номер для следующего сценария.
Команды выполняются последовательно:

```sh
docker compose pause hotel-service
docker compose run --build --rm --no-deps tools outage
docker compose unpause hotel-service
docker compose run --build --rm --no-deps tools recovery
```

Проверка `outage` ожидает 503/504 и сохраненную задачу компенсации с
`releasePending=true`. После `unpause` проверка `recovery` ожидает освобождение
номера фоновым обработчиком, `CANCELLED` и восстановленный счетчик. Пауза сохраняет
память H2, поэтому проверяется именно восстановление после недоступности HTTP.
Если проверка прервана после паузы, `docker compose unpause hotel-service`
возвращает сервис в рабочее состояние.

### Остановка и повторная проверка

```sh
docker compose down
```

Данные обеих H2 в памяти теряются, ключи и учетные данные остаются в volumes.
Для повторной проверки с пустыми БД выполняется `down`, затем `up --build`.
После запуска токены копируются заново. Перезапуск одного бизнес-сервиса
с потерей только его БД не поддерживается. Для полного сброса, включая ключи, пароли и кэш тестовой
сборки, используется `docker compose down --volumes`.

Если стандартные порты заняты, значения из `.env.example` задаются в локальном
`.env` перед запуском. Изменятся только внешние порты. Между собой контейнеры
продолжат обращаться по именам сервисов и внутренним портам.

## Стек

- Java 21, Spring Boot 4.1.1, Spring Cloud BOM 2025.1.4.
- Gradle 9.2.1, Groovy DSL, отдельный Wrapper с SHA-256 дистрибутива у каждого приложения.
- Spring Cloud Gateway Server Web MVC, Eureka, LoadBalancer.
- Spring MVC, Spring Data JPA, H2 in-memory, Bean Validation.
- Spring Security Resource Server и JWT в обоих бизнес-сервисах.
- JUnit Jupiter, HTTP-проверки маршрутизации с локальными тестовыми backend-серверами.
- Flyway.
- Lombok.
- springdoc-openapi 3.2.0 с Swagger UI.

Версии и набор зависимостей объявлены в build.gradle каждого приложения.
H2 Console отключена, Open Session in View отключен. Инфраструктурные
приложения не подключают JPA и H2. [springdoc](https://springdoc.org/getting-started.html)
формирует OpenAPI из контроллеров и DTO бизнес-сервисов.

Схемы бизнес-сервисов создаются Flyway из миграций в собственных каталогах
`src/main/resources/db/migration`. Hibernate использует `ddl-auto: validate`
и проверяет соответствие сущностей схеме, JPA-тесты используют те же миграции.
Booking Service хранит пользователей и бронирования, Hotel Service — отели,
номера и журнал занятости.

В Booking Service миграция V2 добавляет таблицу `bookings`. Каждая запись связана
с локальным пользователем, пара `(user_id, request_id)` уникальна во всех статусах.
Один UUID может использоваться разными пользователями. `room_id` и `hotel_id` —
внешние идентификаторы без связей с БД Hotel Service. Для автоматического подбора
номер может отсутствовать до выбора кандидата.

Бронирование сохраняет способ выбора номера, даты проживания, статус
`PENDING`, `CONFIRMED` или `CANCELLED`, время создания и срок завершения операции.
Даты представлены `LocalDate`, временные отметки — `Instant`.
В БД запрещен пустой или обратный интервал проживания. Новая запись получает
статус `PENDING`. Поле версии используется для оптимистической блокировки.
Флаг `release_pending` и причина `COMPENSATION` или `USER_CANCELLATION` позволяют
хранить незавершенное освобождение номера. Изменения состояния выполняются
в коротких транзакциях с блокировкой записи бронирования, HTTP-вызовы проходят
между ними. Связь с пользователем не допускает каскадного удаления.

Миграция V3 добавляет `next_recovery_at` и индекс очереди восстановления.
Для существующих незавершенных операций время первой попытки берется из
`deadline_at`. Завершенные бронирования в очередь не включаются.
Миграция V4 добавляет индекс личной истории по пользователю, времени создания и `id`.

В Hotel Service таблица `hotels` содержит название до 200 символов и адрес
до 500 символов. Таблица `rooms` хранит ссылку на отель, номер до 32 символов,
флаг операционной доступности и счетчик `times_booked`, изначально равный 0.
Флаг доступности описывает возможность использования номера, например после
ремонта. Занятость по датам определяется журналом резервирований.

Номер уникален внутри своего отеля, в разных отелях одинаковые номера допустимы.
Обязательный внешний ключ не позволяет сохранить номер без существующего отеля
или удалить отель, пока в нем остаются номера. Каскадного удаления нет.
API отелей и номеров проверяет обязательность полей и длину строк до сохранения в БД.

Миграция V2 добавляет `room_reservations`: ссылка на номер, внешний `booking_id`,
UUID `request_id`, даты и состояние `RESERVED` или `RELEASED`. Пара
`(booking_id, room_id)` уникальна независимо от состояния. Связи с таблицами
Booking Service нет, внешний ключ ведет только на локальный номер и запрещает
его удаление при наличии истории. Каскадное удаление записей не настроено.

Для `RESERVED` обязательны обе даты и `start_date < end_date`. Интервал включает
дату начала и исключает дату окончания. Для `RELEASED` допустимо отсутствие обеих
дат: такая запись создается, если отмена приходит раньше подтверждения. Одна
дата без другой и пустой или обратный интервал запрещены ограничением БД.
Каждая операция подтверждения или освобождения выполняется в локальной
транзакции с блокировкой строки номера. Проверка занятости и изменение журнала и счетчика
завершаются вместе. Интервалы пересекаются, если начало каждого раньше конца
другого. Соседние интервалы допустимы.

## Идентификаторы сущностей

Идентификаторы сущностей имеют тип `Long` в Java и `BIGINT` в БД. Это относится
к пользователям, отелям, номерам и бронированиям. `requestId` остается
UUID: он обозначает запрос для проверки идемпотентности.

Маршруты сущностей ограничены цифрами: `/{id:[0-9]+}`. Такой же шаблон используется
в Gateway. Буквы, дробная запись и знак минуса в сегменте ID не подходят маршруту
и дают 404. Нулевой ID и числовое значение за пределами `Long` дают 400.
Именованные операции, например `recommend`, объявляются отдельными маршрутами.

## Разработка в IntelliJ IDEA

Для разработки нужен JDK 21. Репозиторий открывается целиком, а `settings.gradle`
каждого из четырех приложений подключается как отдельный Gradle-проект.
В Project SDK и Gradle JVM используется Java 21. Gradle Wrapper остается у
каждого сервиса, в том числе `gradlew.bat` для Windows.

Сборка и тесты доступны из окна Gradle в IDEA. Из каталога отдельного приложения
`./gradlew build` собирает его с тестами, `./gradlew test` запускает только тесты.
В Windows используются `gradlew.bat build` и `gradlew.bat test`.
Для общей проверки предусмотрена [сборка в Docker](#проверка-требований).

Приложения запускаются из своих классов `*Application` в порядке:
`discovery-server`, `hotel-service`, `booking-service`, `api-gateway`.
Перед запуском из IDE стенд Compose останавливается, чтобы освободить порты.
Для бизнес-сервисов нужны ключи, а для Booking Service — еще и учетные данные
начального ADMIN.

Ключи можно скопировать из работающего Compose-стенда после
[подготовки доступов](#доступы-для-swagger), затем остановить его:

```sh
docker compose cp booking-service:/run/private/jwt-private.pem ./secrets/jwt-private.pem
docker compose cp booking-service:/run/public/jwt-public.pem ./secrets/jwt-public.pem
docker compose down
```

В `Run Configuration → Environment variables` задаются:

| Приложение      | Переменные                                                                                                                                                                          |
|-----------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Hotel Service   | `JWT_PUBLIC_KEY` — абсолютный `file:` URI публичного ключа                                                                                                                          |
| Booking Service | `JWT_PUBLIC_KEY`, `JWT_PRIVATE_KEY` — абсолютные `file:` URI ключей, `BOOTSTRAP_ADMIN_USERNAME` и `BOOTSTRAP_ADMIN_PASSWORD` — значения из `secrets/compose-admin-credentials.json` |

Для Eureka и Gateway дополнительных настроек не нужно. Адрес Eureka и порты
по умолчанию соответствуют таблице приложений в начале README.
Приватный ключ и файлы учетных данных остаются в игнорируемом каталоге `secrets/`.
При запуске из IDE базы пустые. USER регистрируется заново через API,
после чего вход выдает актуальный токен.

## OpenAPI и Swagger UI

| Сервис          | Swagger UI                                          | OpenAPI JSON                              | OpenAPI YAML                                   |
|-----------------|-----------------------------------------------------|-------------------------------------------|------------------------------------------------|
| Booking Service | [Swagger UI](http://localhost:8082/swagger-ui.html) | [JSON](http://localhost:8082/v3/api-docs) | [YAML](http://localhost:8082/v3/api-docs.yaml) |
| Hotel Service   | [Swagger UI](http://localhost:8081/swagger-ui.html) | [JSON](http://localhost:8081/v3/api-docs) | [YAML](http://localhost:8081/v3/api-docs.yaml) |

Документация доступна без токена. Операции защищены теми же правилами, что и при
обычном HTTP-вызове. В `Authorize` поле `userBearer` принимает значение
`accessToken` из входа или регистрации, без префикса `Bearer`. Для административных
операций используется токен ADMIN, для бронирований — USER. Авторизация
не сохраняется Swagger UI между перезагрузками страницы.

В Hotel Service схема `serviceBearer` относится только к подтверждению и
освобождению резервирования. Она требует служебный JWT Booking Service,
пользовательский токен для этих операций не подходит. Самостоятельного публичного
метода выдачи служебного токена нет.

Swagger UI отправляет запросы в открытый бизнес-сервис. Gateway и Eureka не имеют
собственного бизнес-API OpenAPI. На Gateway доступны канонические публичные пути
и перечисленные ниже алиасы, а внутренние операции Hotel Service не маршрутизируются.
В ссылках указаны стандартные порты. В Compose внешние порты меняются через `.env`.
Путь `/v3/api-docs` — стандартный адрес спецификации OpenAPI, бизнес-API сохраняет
версию `/api/v1`.

## Пользовательские JWT

Токен действует один час и содержит идентификатор пользователя в `sub`, роли,
issuer, audience и время выпуска. При проверке времени допускается расхождение
часов до 60 секунд. Аутентификация использует заголовок `Authorization: Bearer`.
Сессии и cookies для нее не используются.

Для JWT используются RSA-ключи размером не менее 2048 бит. Compose создает
ключи на 2048 бит. Публичный ключ имеет формат
X.509 PEM, приватный — PKCS#8 PEM без шифрования. Приватный ключ нужен только
Booking Service, публичный используется обоими бизнес-сервисами. Для запуска
из IDE пути задаются через `JWT_PUBLIC_KEY` и `JWT_PRIVATE_KEY`, как описано
в [разделе разработки](#разработка-в-intellij-idea).

`JWT_ISSUER` по умолчанию равен `hotel-booking`, `JWT_AUDIENCE` — `hotel-api`.
Значения issuer и audience совпадают в обоих бизнес-сервисах. При отсутствии
ключей или неверном формате соответствующий сервис не запускается. Booking Service
также проверяет совпадение публичного и приватного ключей.

Без токена доступны GET /actuator/health, документация OpenAPI/Swagger UI
и POST /api/v1/users/register, /api/v1/users/auth. Маршруты управления пользователями требуют ADMIN,
маршруты бронирований — USER. Остальные пути и методы закрыты.
Ошибки доступа возвращаются как `application/problem+json`: 401 при отсутствии
валидного токена и 403 при недостаточных правах.

## Доступ к Hotel Service

Hotel Service проверяет пользовательский JWT по публичному ключу, без обращения
к Booking Service. Правила одинаковы для прямых запросов и запросов через Gateway.

| Операции                                                        | Доступ         |
|-----------------------------------------------------------------|----------------|
| GET /api/v1/hotels и /api/v1/hotels/{id}                        | USER или ADMIN |
| GET /api/v1/rooms, /api/v1/rooms/{id} и /api/v1/rooms/recommend | USER или ADMIN |
| GET /api/v1/rooms/statistics                                    | ADMIN          |
| POST /api/v1/hotels и /api/v1/rooms                             | ADMIN          |
| PATCH и DELETE /api/v1/hotels/{id} и /api/v1/rooms/{id}         | ADMIN          |

GET /actuator/health остается публичным. Остальные пути и методы закрыты.

## Управление отелями

Маршруты доступны через Gateway и напрямую в Hotel Service по одинаковым адресам.
Чтение разрешено USER и ADMIN, создание, изменение и удаление — ADMIN.

| Метод и путь               | Ответ                 |
|----------------------------|-----------------------|
| POST /api/v1/hotels        | 201, созданный отель  |
| GET /api/v1/hotels         | 200, страница отелей  |
| GET /api/v1/hotels/{id}    | 200, отель            |
| PATCH /api/v1/hotels/{id}  | 200, измененный отель |
| DELETE /api/v1/hotels/{id} | 204, без тела         |

Отель представлен полями `id`, `name` и `address`. Создание принимает `name`
и `address`: непустые строки длиной до 200 и 500 символов соответственно.
Строки из одних пробельных символов отклоняются, остальные значения сохраняются
без обрезания пробелов. Числа и boolean вместо строк, неизвестные поля и
некорректный JSON дают 400 с кодом `INVALID_REQUEST_BODY`.

Список принимает `page` от 0 и `size` от 1 до 100, по умолчанию 20. Ответ содержит
`content`, `page`, `size`, `totalElements`, порядок — по возрастанию id.
За пределами списка возвращается пустая страница с тем же общим количеством.

В `PATCH` пропущенное поле остается прежним. Явный `null` дает 400
`INVALID_REQUEST_BODY`, пустой объект и нарушения ограничений строк — 400
`VALIDATION_FAILED`. Такой же код используется для неверных значений page,
size и нулевого id. Переполнение числового ID и неверный тип query-параметра
дают 400 `INVALID_REQUEST_PARAMETERS`.

Отсутствующий отель возвращает 404 `HOTEL_NOT_FOUND`. Если в отеле есть номера,
удаление возвращает 409 `HOTEL_HAS_ROOMS`, отель и номера сохраняются.
После удаления последнего номера отель можно удалить, повторное удаление
отсутствующего отеля возвращает 404.

## Управление номерами

Номера создаются в существующем отеле. Прямые запросы в Hotel Service и запросы
через Gateway используют одинаковые пути и правила доступа.

| Метод и путь              | Доступ         | Ответ                 |
|---------------------------|----------------|-----------------------|
| POST /api/v1/rooms        | ADMIN          | 201, созданный номер  |
| GET /api/v1/rooms/{id}    | USER или ADMIN | 200, номер            |
| PATCH /api/v1/rooms/{id}  | ADMIN          | 200, измененный номер |
| DELETE /api/v1/rooms/{id} | ADMIN          | 204, без тела         |

Создание принимает `hotelId`, `number` и `available`. Идентификатор отеля —
положительное целое JSON-число, номер — непустая строка до 32 символов,
`available` — boolean. Пробелы внутри и по краям номера сохраняются, строка
из одних пробельных символов отклоняется. Преобразование строк и чисел
в другие типы не выполняется.

Ответ содержит `id`, `hotelId`, `number`, `available` и `timesBooked`.
Счетчик начинается с 0, в запросах его задавать нельзя. `PATCH` принимает только
`number` и `available`: пропущенное поле сохраняется, явный `null`, неизвестное
поле и неверный тип дают 400 `INVALID_REQUEST_BODY`. Пустой объект, пустой номер
или превышение длины дают 400 `VALIDATION_FAILED`. Изменение `hotelId` не поддерживается.

Одинаковые номера в одном отеле дают 409 `ROOM_NUMBER_ALREADY_EXISTS`, в разных
отелях они допустимы. Конфликт при изменении откатывает весь запрос, включая
изменение доступности. Отсутствующий отель при создании дает 404 `HOTEL_NOT_FOUND`,
отсутствующий номер — 404 `ROOM_NOT_FOUND`. Удаление номера сохраняет сам отель,
повторное удаление возвращает 404.

Поиск по датам и рекомендации доступны через GET `/api/v1/rooms` и
`/api/v1/rooms/recommend`, статистика — через GET `/api/v1/rooms/statistics`.
Удаление номера с любой историей резервирования дает 409 `ROOM_HAS_RESERVATIONS`, включая записи
`RELEASED` без дат. Отключение номера при действующем текущем или будущем
резервировании дает 409 `ROOM_HAS_FUTURE_RESERVATIONS`: проверяется `RESERVED`
с датой окончания позже текущей даты UTC. Завершившееся сегодня или освобожденное
резервирование отключению не мешает. Номер комнаты можно менять и при наличии
будущих резервирований. Проверки и изменения используют ту же блокировку,
что внутренние операции, поэтому
изменение остальных полей при конфликте также откатывается.

## Поиск номеров и рекомендации

Оба запроса доступны USER и ADMIN, напрямую в Hotel Service и через Gateway:

```http
GET /api/v1/rooms?startDate=2027-01-11&endDate=2027-01-13&hotelId=1&page=0&size=20
GET /api/v1/rooms/recommend?startDate=2027-01-11&endDate=2027-01-13&hotelId=1&page=0&size=20
```

`startDate` и `endDate` обязательны, передаются датами `YYYY-MM-DD` без времени
и задают интервал с исключенным концом. Начало строго раньше окончания.
Поиск возможен и за прошедшие даты. Необязательный положительный `hotelId`
ограничивает выборку отелем. Без него поиск охватывает все отели, а фильтр по
несуществующему отелю возвращает пустую страницу.

В выдачу входят только номера с `available=true`, для которых нет пересекающихся
резервирований `RESERVED`. Соседние интервалы и записи `RELEASED`, включая записи
без дат, поиску не мешают. Обычный список отсортирован по `id` по возрастанию.
В рекомендациях сначала идут номера с меньшим `timesBooked`, затем с меньшим `id`. Номера с меньшим историческим
числом бронирований оказываются раньше, без статистических моделей.

Ответ имеет поля `{content, page, size, totalElements}`, элементы `content`
совпадают с ответом просмотра номера. `page` начинается с 0, `size` — от 1 до 100,
по умолчанию 20. `totalElements` учитывает всю отфильтрованную выборку. Страница
за ее пределами пустая, общее количество при этом сохраняется.

Пропущенные даты и неверные типы параметров дают 400 `INVALID_REQUEST_PARAMETERS`.
Нарушение порядка дат, диапазона страницы, размера или ID отеля дает
400 `VALIDATION_FAILED`. Поиск не меняет журнал и счетчики, найденный номер
не резервируется: подтверждение заново проверяет занятость под блокировкой.

## Статистика занятости

GET `/api/v1/rooms/statistics` доступен только ADMIN, напрямую в Hotel Service
и через Gateway. Например:

```http
GET /api/v1/rooms/statistics?startDate=2027-01-10&endDate=2027-01-20&hotelId=1&page=0&size=20
```

Обязательные даты, необязательный `hotelId` и пагинация используют те же правила,
что поиск номеров. В отчет входят все номера выбранного отеля, включая
недоступные и не имеющие резервирований. Без фильтра учитываются все отели,
при неизвестном отеле возвращается пустая страница. Порядок — по `roomId`
по возрастанию. Ответ содержит `{content, page, size, totalElements}`.

Каждый элемент `content` имеет поля `roomId`, `timesBooked`, `bookedNights`,
`totalNights` и `occupancyRate`. `totalNights` — длительность запрошенного
интервала, его конец не включен. В `bookedNights` суммируются только пересечения
записей `RESERVED` с этим периодом: часть резервирования за пределами отчета
не учитывается, соседние интервалы и записи `RELEASED` дают нулевой вклад.

`occupancyRate` — доля занятых ночей от 0 до 1: четыре ночи из десяти дают `0.4`.
При отсутствии занятости `bookedNights` и `occupancyRate` равны нулю. `timesBooked` остается накопленным
историческим счетчиком номера, поэтому не ограничивается периодом отчета.
Суммирование выполняется в БД. Чтение статистики не меняет журнал и счетчики.

## Межсервисные JWT

Для POST /api/v1/rooms/{id}/confirm-availability и /api/v1/rooms/{id}/release
предусмотрена отдельная аутентификация. Booking Service выпускает токен через
`InternalTokenService`, который используется HTTP-клиентом бронирований.
Публичного эндпоинта выдачи служебных токенов нет.

Служебный JWT подписывается тем же приватным RSA-ключом, что и пользовательский,
но содержит `sub=booking-service`, `scope=reservations:write` и отдельный audience.
Время действия — 120 секунд, допустимое расхождение часов — 60 секунд.
`SERVICE_JWT_AUDIENCE` задается одинаково в обоих бизнес-сервисах и по умолчанию
равен `hotel-internal`. Совпадение с `JWT_AUDIENCE` останавливает запуск.
Issuer берется из `JWT_ISSUER`.

Пользовательские токены, включая ADMIN, получают 401 на внутренних операциях.
Корректный служебный токен без права `reservations:write` получает 403.
Служебный токен не подходит для публичного API Hotel Service и Booking Service.
Gateway не публикует внутренние пути, даже при наличии служебного токена.

Внутренние операции принимают JSON и возвращают 200 с
`{bookingId, roomId, state}`, где состояние равно `RESERVED` или `RELEASED`:

| Метод и путь                                 | Поля запроса                             |
|----------------------------------------------|------------------------------------------|
| POST /api/v1/rooms/{id}/confirm-availability | bookingId, requestId, startDate, endDate |
| POST /api/v1/rooms/{id}/release              | bookingId, requestId, reason             |

Все поля обязательны. `bookingId` — положительное целое число типа Long,
`requestId` — UUID, даты — строки ISO `YYYY-MM-DD` с `startDate < endDate`.
Причина освобождения — строка `COMPENSATION` или `USER_CANCELLATION`.
Неизвестные поля, числовые enum и подмена типов отклоняются. Ошибки формы JSON
дают 400 `INVALID_REQUEST_BODY`, нарушения обязательности, диапазона ID или
порядка дат — 400 `VALIDATION_FAILED`. Отсутствующий номер дает 404 `ROOM_NOT_FOUND`.
Начало проживания проверяется относительно текущей даты в Booking Service
при создании бронирования. Внутренний протокол допускает отложенные повторы.

Повторное подтверждение с теми же идентификаторами и датами возвращает прежний
результат без изменения счетчика. Другой `requestId` для пары бронирование/номер
или другие даты уже принятого `RESERVED` дают 409 `IDEMPOTENCY_CONFLICT`.
Занятый или операционно недоступный номер дает 409 `ROOM_UNAVAILABLE`.
Подтверждение после освобождения дает 409 `RESERVATION_RELEASED` независимо от
наличия дат в освобожденной записи. При проверке сначала сверяется `requestId`.

При новом подтверждении `timesBooked` увеличивается один раз. `COMPENSATION`
освобождает интервал и уменьшает счетчик один раз. При `USER_CANCELLATION`
исторический счетчик сохраняется. Освобождение без предшествующего подтверждения создает
`RELEASED` без дат и не меняет счетчик. Состояние `RELEASED` окончательное:
повторное освобождение ничего не меняет, в том числе при другой причине.

Подтверждение, освобождение, изменение и удаление номера используют блокировку
`PESSIMISTIC_WRITE`. Ожидание ограничено двумя секундами. При конфликте блокировки
возвращается 503 `ROOM_BUSY` без внутренних сведений БД. Hotel Service и Gateway
не повторяют эти операции автоматически. Гарантии относятся к сохраненному
состоянию одной H2, ограничения ее жизненного цикла остаются прежними.

## Создание бронирования

`POST /api/v1/bookings` доступен с ролью USER через Gateway и напрямую в Booking
Service. ADMIN без роли USER не получает доступ. Пользователь определяется по JWT,
поле `userId` в JSON не допускается.

```json
{
  "requestId": "ec9429e7-e8c1-40c2-b260-63626ee33428",
  "autoSelect": false,
  "roomId": 42,
  "startDate": "2027-01-10",
  "endDate": "2027-01-12"
}
```

При явном выборе обязательны UUID `requestId`, `autoSelect=false`, положительный
целочисленный `roomId` и обе даты, а `hotelId` не передается.
Для автоматического подбора указывается `autoSelect=true` и положительный `hotelId`.
Поле `roomId` игнорируется, в том числе при сравнении повторных запросов.
Неизвестные поля, строковые числа и логические значения,
дробные ID, массивы и время вместо календарной даты отклоняются.
Для нового запроса начало не предшествует текущей дате UTC, конец строго позже
начала. Пример использует конкретные даты, которые при необходимости заменяются
на актуальный период.

Booking Service сначала сохраняет `PENDING`, затем обращается напрямую к
Hotel Service через Eureka и Spring Cloud LoadBalancer. Подтверждение и
освобождение номера используют служебный JWT.
Успешное резервирование переводит запись в `CONFIRMED`, ответ — 201.
Тело содержит `id`, `requestId`, `roomId`, `startDate`, `endDate`, `status`,
`createdAt` и `releasePending`. Заголовок `Location` указывает
`/api/v1/bookings/{id}`. Получение по этому адресу доступно владельцу бронирования.

При автоматическом подборе Booking Service запрашивает первую страницу из 20
рекомендаций Hotel Service для указанных отеля и дат, передавая JWT пользователя.
Номера рассматриваются по `timesBooked`, при равенстве — по ID. Кандидат сохраняется
в бронировании до подтверждения. Если номер успели занять, он освобождается с
причиной `COMPENSATION`, после чего проверяется следующий кандидат этой страницы.
Пустой список или занятые кандидаты дают 409 `ROOM_UNAVAILABLE` и `CANCELLED`.
При сетевом сбое или неопределенном результате подтверждения подбор прекращается,
а выбранный номер освобождается через обычную компенсацию и фоновое восстановление.
Отмена или истечение срока операции не допускают выбора следующего номера.

Повтор того же запроса возвращает сохраненную запись с 200, а пока первая
операция выполняется — `PENDING` с 202 и `Location`. Нового резервирования нет.
Проверка уже принятого запроса выполняется до проверки дат относительно сегодняшнего
дня, поэтому повтор после окончания периода остается допустимым. Другие параметры
под тем же UUID дают 409 `IDEMPOTENCY_CONFLICT`. UUID ограничен пользователем,
разные пользователи могут применять одинаковое значение.

При ошибке бронирование становится `CANCELLED` с задачей освобождения номера.
Освобождение с причиной `COMPENSATION` выполняется и при потерянном ответе
подтверждения, поскольку удаленное резервирование могло завершиться.
После освобождения `releasePending` сбрасывается. Ответ `ROOM_NOT_FOUND` тоже
завершает задачу, поскольку у отсутствующего номера не может быть резервирований.
Повтор отмененного запроса возвращает ту же запись и не запускает создание заново.

Занятый номер дает 409 `ROOM_UNAVAILABLE`, отсутствующий — 404 `ROOM_NOT_FOUND`.
Сбой зависимости возвращает 503 `HOTEL_SERVICE_UNAVAILABLE`, таймаут HTTP-клиента
или исчерпание бюджета — 504 `BOOKING_TIMEOUT`. Если отмена опередила подтверждение, возвращается
409 `BOOKING_CANCELLED`. Ошибка сохранения состояния дает 503
`BOOKING_STORAGE_UNAVAILABLE`. Ошибки после создания записи содержат `bookingId`
и `releasePending`, внутренние ответы и диагностические сообщения не раскрываются.

Таймауты и паузы Booking Service задаются в миллисекундах:

| Переменная                   | По умолчанию | Назначение                                               |
|------------------------------|--------------|----------------------------------------------------------|
| HOTEL_CONNECT_TIMEOUT_MS     | 1000         | Таймаут соединения, от 1 до 60000                        |
| HOTEL_READ_TIMEOUT_MS        | 2000         | Таймаут получения ответа, от 1 до 60000                  |
| HOTEL_MAX_ATTEMPTS           | 3            | Число попыток каждого запроса к Hotel Service, от 1 до 5 |
| HOTEL_BACKOFF_MS             | 100          | Начальная пауза повторов, от 1 до 1000                   |
| BOOKING_OPERATION_TIMEOUT_MS | 10000        | Срок операции, от 1 до 120000                            |

Пауза растет экспоненциально с разбросом от половины до полного значения,
максимум — 1000 мс. Повторяются сетевые ошибки, таймауты и ответы 502/503/504.
Другие ответы не повторяются как временные сбои. Срок операции ограничивает
HTTP-попытки и паузы, включая компенсацию, и проверяется перед сохранением
`CONFIRMED`. Gateway и LoadBalancer не добавляют повторов записи, перенаправления
HTTP-клиент не выполняет.

Если освобождение не удалось или бюджет времени закончился, в БД остается
`CANCELLED` с `releasePending=true`. При недоступной БД может остаться `PENDING`.
Повтор POST показывает сохраненное состояние, а фоновый обработчик завершает
отмену и освобождение номера.

## История бронирований

Чтение доступно с ролью USER через Gateway и напрямую в Booking Service.
Владелец определяется по JWT, ADMIN без роли USER получает 403.

| Метод и путь              | Ответ                        |
|---------------------------|------------------------------|
| GET /api/v1/bookings      | 200, страница личной истории |
| GET /api/v1/bookings/{id} | 200, свое бронирование       |

История включает `PENDING`, `CONFIRMED` и `CANCELLED`, сначала идут более новые
записи по `createdAt`, при одинаковом времени — меньший `id`. Параметры `page`
и `size` задают страницу с нуля и размер от 1 до 100, по умолчанию — 20.
Например, `GET /api/v1/bookings?page=0&size=20`. Ответ содержит `content`, `page`,
`size`, `totalElements`, причем общее количество относится только к текущему
пользователю. Пустая история и страница за пределами списка возвращаются с 200.

Бронирование имеет тот же формат, что и ответ создания. Поле `releasePending`
показывает текущее состояние освобождения номера. До выбора номера `roomId`
может быть `null`. Данные читаются из БД Booking Service, поэтому просмотр
доступен и при недоступном Hotel Service.

Чужое и отсутствующее бронирование возвращают одинаковый 404
`BOOKING_NOT_FOUND` с сообщением `Booking not found`. Некорректные параметры
пагинации дают 400. Для `id` действуют общие правила числовых маршрутов.

## Отмена бронирования

`DELETE /api/v1/bookings/{id}` доступен владельцу с ролью USER. Запись остается
в личной истории со статусом `CANCELLED`. Ответ содержит тот же объект,
что и просмотр по ID, а `Location` указывает канонический адрес бронирования.

При завершенном освобождении или отсутствии выбранного номера возвращается
200 с `releasePending=false`. Если освобождение еще требуется, ответ — 202
с `releasePending=true`. Текущее состояние доступно через GET по `Location`.
Повторный DELETE возвращает текущее состояние, сохраняя первоначальную причину
отмены и время фоновой попытки. Повторное освобождение выполняет фоновый обработчик.

При отмене `PENDING` сохраняется причина `COMPENSATION`: незавершенное создание
может быть отменено, даже если подтверждение Hotel Service еще выполняется.
Если резервирование уже произошло, компенсация уменьшает счетчик номера один раз.
Для `CONFIRMED` используется `USER_CANCELLATION`, которая освобождает даты
и сохраняет исторический `timesBooked`.

Статус и причина выбираются под блокировкой записи Booking Service.
Если подтверждение опередило отмену, сохраняется `USER_CANCELLATION`.
Если первой завершилась отмена, поздний ответ подтверждения оставляет
бронирование в `CANCELLED`. Hotel Service обрабатывает повторные освобождения
идемпотентно с исходными `bookingId` и `requestId`.

После сохранения отмены освобождение выполняется вне транзакции. Для него
выделяется новое окно `BOOKING_OPERATION_TIMEOUT_MS`, независимо от срока
исходного создания. После этого окна задача доступна фоновому обработчику.
Ошибка Hotel Service или сохранения подтверждения освобождения оставляет 202
и задачу в БД. Если не удалось сохранить саму отмену, возвращается 503
`BOOKING_STORAGE_UNAVAILABLE`.

Чужое и отсутствующее бронирование возвращают одинаковый 404 `BOOKING_NOT_FOUND`.
Для некорректного `id` действуют общие правила числовых маршрутов, ADMIN без
роли USER получает 403.

## Фоновое восстановление бронирований

Обработчик включен по умолчанию. Он выбирает задачи по времени следующей попытки
и `id`, ограничивая размер порции. Просроченный `PENDING` становится `CANCELLED`
с причиной `COMPENSATION`. Если номер еще не выбран, освобождение не требуется.
Подтвержденные бронирования не отменяются по таймеру.

Перед HTTP-вызовом запись блокируется, ее состояние проверяется повторно,
а время следующей попытки сохраняется в БД. Поэтому второй обработчик не захватит
ту же задачу, пока действует окно текущей попытки. Блокировка снимается до
обращения к Hotel Service. Причина освобождения сохраняется при повторах, в том
числе `USER_CANCELLATION` для пользовательской отмены.

Успешный `release` снимает `releasePending` и убирает задачу из очереди.
При ошибке она остается в БД и снова становится доступной после срока попытки
и паузы повтора. Ошибка одной записи не останавливает обработку остальных.
Ни перезапуск обработчика, ни потеря ответа освобождения не создают новое
бронирование: используется прежняя пара `bookingId`/`requestId`, а повторное
освобождение идемпотентно в Hotel Service. Запоздалая ошибка старого обработчика
не возвращает уже завершенную задачу в очередь.

| Переменная                        | По умолчанию | Назначение                                                             |
|-----------------------------------|--------------|------------------------------------------------------------------------|
| BOOKING_RECOVERY_ENABLED          | true         | Включение фонового обработчика                                         |
| BOOKING_RECOVERY_BATCH_SIZE       | 20           | Размер порции, от 1 до 100                                             |
| BOOKING_RECOVERY_POLL_INTERVAL_MS | 5000         | Пауза после цикла и перед первым запуском, от 1 до 3600000 мс          |
| BOOKING_RECOVERY_RETRY_DELAY_MS   | 5000         | Пауза после срока попытки перед повторным захватом, от 1 до 3600000 мс |
| BOOKING_RECOVERY_CYCLE_TIMEOUT_MS | 10000        | Бюджет цикла, от 1 до 120000 мс                                        |

Один цикл выполняется последовательно в управляемом Spring потоке. Срок
HTTP-попытки ограничен оставшимся бюджетом цикла и `BOOKING_OPERATION_TIMEOUT_MS`.
Повторы внутри вызова выполняет `HotelServiceGateway` по настройкам `HOTEL_*`.
Проверка бюджета между записями не прерывает уже начатую транзакцию.
Ожидание блокировки записи ограничено двумя секундами.

При сохраненной БД обработчик продолжает работу после перезапуска, включая
задачи с истекшим окном захвата. Это проверяется на файловой H2. Стандартный
локальный стенд использует H2 in-memory и теряет данные при остановке процесса,
поэтому восстановление после потери БД по-прежнему не поддерживается.

## Регистрация и вход

Публичные адреса имеют вид `/api/v1/resource`, например `/api/v1/users/register`.
Такая же структура используется для совместимых маршрутов Gateway.
Actuator и Eureka сохраняют свои стандартные адреса.

Оба запроса принимают JSON с полями `username` и `password`. Username уникален
с учетом регистра и содержит от 3 до 64 латинских букв, цифр или символов `_.-`.
Пароль занимает от 12 до 72 байт в UTF-8 и используется без обрезания пробелов
или нормализации. Неизвестные поля отклоняются, роль при регистрации всегда USER.

| Метод и путь                | Ответ                                                          |
|-----------------------------|----------------------------------------------------------------|
| POST /api/v1/users/register | 201, объект `user` с id, username, role и объект `token`       |
| POST /api/v1/users/auth     | 200, объект с accessToken, tokenType: Bearer и expiresIn: 3600 |

Маршруты доступны на Gateway (порт 8080) и напрямую в Booking Service (порт 8082).
Для запросов с подготовленным JSON-файлом secrets/credentials.json:

```sh
curl http://localhost:8080/api/v1/users/register -H 'Content-Type: application/json' --data-binary @secrets/credentials.json
curl http://localhost:8080/api/v1/users/auth -H 'Content-Type: application/json' --data-binary @secrets/credentials.json
```

Неверные данные запроса возвращают 400. Ошибки в полях перечисляются в `violations`
без введенных значений. Занятый username дает 409 с кодом `USERNAME_ALREADY_EXISTS`,
а неизвестный пользователь и неверный пароль — одинаковый ответ 401
`INVALID_CREDENTIALS`. Пароли и хеши отсутствуют в ответах.

## Начальный администратор

В Booking Service предусмотрено создание первого аккаунта ADMIN при запуске.
Инициализация включена по умолчанию, встроенных логина и пароля нет.
Параметры задаются в окружении Booking Service:

| Переменная               | По умолчанию | Назначение                               |
|--------------------------|--------------|------------------------------------------|
| BOOTSTRAP_ADMIN_ENABLED  | true         | Отключение инициализации значением false |
| BOOTSTRAP_ADMIN_USERNAME | Не задано    | Логин администратора                     |
| BOOTSTRAP_ADMIN_PASSWORD | Не задано    | Пароль администратора                    |

В Compose логин и случайный пароль готовятся автоматически и передаются
через `configtree`. Файл `compose-admin-credentials.json` доступен после
[копирования доступов](#доступы-для-swagger). При запуске из IDE эти же значения
задаются в окружении Booking Service.

При включенной инициализации обязательны оба значения, даже если аккаунт уже
существует. К ним применяются те же ограничения, что при регистрации:
от 3 до 64 символов `[A-Za-z0-9_.-]` в логине и от 12 до 72 байт UTF-8 в пароле.
Отсутствующие или некорректные значения останавливают запуск, сообщение об ошибке
содержит только названия полей. При выключенной инициализации учетные данные
не проверяются и аккаунт не создается.

Пароль нового администратора хранится как хеш bcrypt. Если указанный логин уже
принадлежит ADMIN, аккаунт сохраняется без изменений, в том числе при другом
пароле в конфигурации. Совпадение с логином USER останавливает запуск сервиса
без повышения роли. Эта настройка предназначена для создания аккаунта, смена
пароля через нее не выполняется.

Вход администратора использует обычный POST `/api/v1/users/auth` и возвращает
JWT с ролью ADMIN. Поскольку H2 работает в памяти, после остановки приложения
аккаунт теряется и при следующем запуске создается заново, если инициализация включена.

## Управление пользователями

Все операции доступны только с JWT роли ADMIN, как напрямую в Booking Service,
так и через Gateway. Создание принимает `username`, `password` и обязательную
строковую роль `USER` или `ADMIN`. Ограничения логина и пароля совпадают с регистрацией.

| Метод и путь              | Ответ                         |
|---------------------------|-------------------------------|
| POST /api/v1/users        | 201, созданный пользователь   |
| GET /api/v1/users         | 200, страница пользователей   |
| GET /api/v1/users/{id}    | 200, пользователь             |
| PATCH /api/v1/users/{id}  | 200, обновленный пользователь |
| DELETE /api/v1/users/{id} | 204, без тела                 |

Пользователь представлен полями `id`, `username`, `role`, пароли и хеши в ответы
не включаются. Список отсортирован по `id` по возрастанию. Параметр `page` начинается
с нуля, `size` принимает значения от 1 до 100, по умолчанию — 20. Ответ содержит
`content`, `page`, `size`, `totalElements`. Страница за пределами списка пуста.
Идентификатор пользователя — положительное число типа Long.

PATCH принимает любое непустое подмножество полей `username`, `password`, `role`.
Отсутствующее поле сохраняет свое значение, явный `null` и неизвестные поля
отклоняются с 400. Например, `{"role":"ADMIN"}` меняет только роль.
Новый пароль хешируется, остальные изменения не затрагивают сохраненный хеш.

Некорректные поля и параметры пагинации возвращают 400. Для ID действуют
общие правила числовых маршрутов, описанные выше.
Отсутствующий пользователь дает 404 с кодом `USER_NOT_FOUND`, занятый username —
409 `USERNAME_ALREADY_EXISTS`. При конфликте все изменение откатывается.
Повторное удаление уже отсутствующего пользователя возвращает 404.
При наличии хотя бы одного бронирования в любом статусе удаление возвращает
409 `USER_HAS_BOOKINGS`, пользователь и его история сохраняются. Внешний ключ
защищает историю, если бронирование появилось после предварительной проверки.

JWT сохраняет выданные права до истечения срока действия. Изменение роли или пароля,
как и удаление аккаунта, не отзывает уже выпущенные токены. После входа с актуальными
учетными данными новый токен содержит текущую роль.

## Совместимые маршруты Gateway

Дополнительные адреса доступны на Gateway и преобразуются в канонические пути
Booking Service. Метод, JSON, заголовок Authorization, query-параметры и ответ
сервиса сохраняются.

| Маршрут Gateway             | Путь Booking Service   |
|-----------------------------|------------------------|
| POST /api/v1/user/register  | /api/v1/users/register |
| POST /api/v1/user/auth      | /api/v1/users/auth     |
| POST /api/v1/user           | /api/v1/users          |
| PATCH /api/v1/user?id={id}  | /api/v1/users/{id}     |
| DELETE /api/v1/user?id={id} | /api/v1/users/{id}     |
| POST /api/v1/booking        | /api/v1/bookings       |
| GET /api/v1/booking/{id}    | /api/v1/bookings/{id}  |
| DELETE /api/v1/booking/{id} | /api/v1/bookings/{id}  |

Для PATCH и DELETE алиаса `/api/v1/user` обязателен один положительный `id` в query-параметрах.
Отсутствующее, повторенное, некорректное или выходящее за диапазон Long значение
возвращает 400 `INVALID_REQUEST_PARAMETERS` без обращения к Booking Service.
Неверсионированные адреса и неуказанные методы не маршрутизируются.

## Сквозной пример запросов

Ниже приведен необязательный пример для Bash с `curl` и Python 3. Проверка через
[Swagger](#openapi-и-swagger-ui) и `tools check` доступна без этих утилит на хосте.

Пример выполняется из корня репозитория после запуска Compose и копирования
доступов. Он создает пользователя `hotel_guest`, отель и номера. При повторном
выполнении имя пользователя должно быть новым или стенд должен быть сброшен.
Учетные данные ADMIN берутся из `secrets/compose-admin-credentials.json`.
Даты вычисляются относительно текущего дня UTC. Если внешний порт Gateway
изменен, это учитывается в `BASE_URL`.

Подготовка USER и получение двух токенов:

```sh
BASE_URL=http://localhost:8080

json_value() {
  python3 -c 'import json, sys; print(json.load(sys.stdin)[sys.argv[1]])' "$1"
}

umask 077
python3 - <<'PYTHON'
import getpass
import json
from pathlib import Path

credentials = {"username": "hotel_guest", "password": getpass.getpass("Guest password: ")}
Path("secrets/guest-credentials.json").write_text(json.dumps(credentials), encoding="utf-8")
PYTHON

ADMIN_TOKEN=$(curl --fail-with-body --silent --show-error "$BASE_URL/api/v1/users/auth" \
  -H 'Content-Type: application/json' --data-binary @secrets/compose-admin-credentials.json | json_value accessToken)
curl --fail-with-body --silent --show-error "$BASE_URL/api/v1/users/register" \
  -H 'Content-Type: application/json' --data-binary @secrets/guest-credentials.json > /dev/null
USER_TOKEN=$(curl --fail-with-body --silent --show-error "$BASE_URL/api/v1/users/auth" \
  -H 'Content-Type: application/json' --data-binary @secrets/guest-credentials.json | json_value accessToken)
```

ADMIN создает отель и два номера. Оба токена используются в отдельных заголовках,
поскольку роль ADMIN сама по себе не дает доступ к пользовательским бронированиям.

```sh
HOTEL_ID=$(curl --fail-with-body --silent --show-error "$BASE_URL/api/v1/hotels" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  --data '{"name":"City Hotel","address":"Central Street, 15"}' | json_value id)
ROOM_ID=$(curl --fail-with-body --silent --show-error "$BASE_URL/api/v1/rooms" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  --data "{\"hotelId\":$HOTEL_ID,\"number\":\"101\",\"available\":true}" | json_value id)
curl --fail-with-body --silent --show-error "$BASE_URL/api/v1/rooms" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  --data "{\"hotelId\":$HOTEL_ID,\"number\":\"102\",\"available\":true}"

START_DATE=$(python3 -c 'from datetime import datetime, timedelta, timezone; print((datetime.now(timezone.utc).date() + timedelta(days=7)).isoformat())')
END_DATE=$(python3 -c 'from datetime import datetime, timedelta, timezone; print((datetime.now(timezone.utc).date() + timedelta(days=9)).isoformat())')
curl --fail-with-body --silent --show-error --get "$BASE_URL/api/v1/rooms/recommend" \
  -H "Authorization: Bearer $USER_TOKEN" \
  --data-urlencode "hotelId=$HOTEL_ID" --data-urlencode "startDate=$START_DATE" \
  --data-urlencode "endDate=$END_DATE" --data-urlencode 'page=0' --data-urlencode 'size=20'
```

Первый запрос создает явное бронирование с 201. Повтор использует тот же UUID
и JSON, возвращает ту же запись с 200. Новый UUID с `autoSelect=true` бронирует
оставшийся свободный номер. Повтор UUID с измененными значимыми полями дает 409
`IDEMPOTENCY_CONFLICT`.

```sh
REQUEST_ID=$(python3 -c 'import uuid; print(uuid.uuid4())')
BOOKING_REQUEST=$(cat <<JSON
{
  "requestId": "$REQUEST_ID",
  "autoSelect": false,
  "roomId": $ROOM_ID,
  "startDate": "$START_DATE",
  "endDate": "$END_DATE"
}
JSON
)
BOOKING_ID=$(curl --fail-with-body --silent --show-error "$BASE_URL/api/v1/bookings" \
  -H "Authorization: Bearer $USER_TOKEN" -H 'Content-Type: application/json' \
  --data "$BOOKING_REQUEST" | json_value id)
curl --fail-with-body --silent --show-error "$BASE_URL/api/v1/bookings" \
  -H "Authorization: Bearer $USER_TOKEN" -H 'Content-Type: application/json' \
  --data "$BOOKING_REQUEST"

AUTO_REQUEST_ID=$(python3 -c 'import uuid; print(uuid.uuid4())')
curl --fail-with-body --silent --show-error "$BASE_URL/api/v1/bookings" \
  -H "Authorization: Bearer $USER_TOKEN" -H 'Content-Type: application/json' --data-binary @- <<JSON
{
  "requestId": "$AUTO_REQUEST_ID",
  "autoSelect": true,
  "hotelId": $HOTEL_ID,
  "startDate": "$START_DATE",
  "endDate": "$END_DATE"
}
JSON
```

Просмотр, статистика и отмена первого бронирования:

```sh
curl --fail-with-body --silent --show-error "$BASE_URL/api/v1/bookings?page=0&size=20" \
  -H "Authorization: Bearer $USER_TOKEN"
curl --fail-with-body --silent --show-error "$BASE_URL/api/v1/bookings/$BOOKING_ID" \
  -H "Authorization: Bearer $USER_TOKEN"
curl --fail-with-body --silent --show-error --get "$BASE_URL/api/v1/rooms/statistics" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  --data-urlencode "hotelId=$HOTEL_ID" --data-urlencode "startDate=$START_DATE" \
  --data-urlencode "endDate=$END_DATE"
curl --fail-with-body --silent --show-error -X DELETE "$BASE_URL/api/v1/bookings/$BOOKING_ID" \
  -H "Authorization: Bearer $USER_TOKEN"
curl --fail-with-body --silent --show-error -X DELETE "$BASE_URL/api/v1/bookings/$BOOKING_ID" \
  -H "Authorization: Bearer $USER_TOKEN"
```

При работающем Hotel Service обе отмены возвращают 200 с `CANCELLED` и
`releasePending=false`, исторический счетчик не уменьшается. При сбое освобождения
возможен 202 с `releasePending=true`, затем задачу завершает фоновый обработчик.
Второе, автоматически выбранное бронирование остается подтвержденным.

## Проверка проекта

[Команды проверки через Compose](#проверка-требований) запускают HTTP-сценарии
и полную сборку четырех приложений с тестами.

Тесты проверяют JWT и роли, валидацию JSON, миграции и запросы H2, конкурирующие
резервирования, идемпотентность, компенсацию и восстановление, маршруты Gateway
и спецификации OpenAPI. У них свои ключи и БД, поэтому работающий стенд не нужен.
Сквозной пример выше показывает пользовательские операции через Gateway,
Eureka и оба бизнес-сервиса.
