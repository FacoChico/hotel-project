# Hotel Project

REST API системы бронирования отелей. Один репозиторий содержит четыре
независимых Spring Boot приложения, каждое собирается своим Gradle Wrapper
без исходников, библиотек и корневой сборки остальных приложений.

## Состояние реализации

Реализован инфраструктурный каркас: Eureka Server,
Gateway с явными маршрутами, два бизнес-приложения с отдельными H2.
В Booking Service добавлены сущность пользователя, роли USER/ADMIN и репозиторий,
username уникален с учётом регистра, поле password предназначено для хеша пароля.
Booking Service выпускает JWT с подписью RS256 и проверяет токены на входящих
запросах. Регистрация и вход доступны через Gateway, пароли хранятся как хеши
bcrypt. Начальный администратор создаётся при включении инициализации
через внешнюю конфигурацию. Права доступа разделены между USER и ADMIN.
ADMIN может создавать, просматривать, изменять и удалять пользователей.
Оба бизнес-сервиса самостоятельно проверяют JWT. Hotel Service разграничивает
публичные запросы по ролям, а для внутренних операций принимает отдельный
служебный токен Booking Service. В Hotel Service добавлены сущности отеля и номера
с репозиториями и миграцией БД. API отелей и номеров, как и бронирования, пока
не реализованы: после успешной проверки доступа запросы к разрешённым путям получают 404.
Без токена защищённые маршруты возвращают 401.

## Стек

- Java 21, Spring Boot 4.1.1, Spring Cloud BOM 2025.1.3.
- Gradle 9.2.1, Groovy DSL, отдельный Wrapper с SHA-256 дистрибутива у каждого приложения.
- Spring Cloud Gateway Server Web MVC, Eureka, LoadBalancer.
- Spring MVC, Spring Data JPA, H2 in-memory, Bean Validation.
- Spring Security Resource Server и JWT в обоих бизнес-сервисах.
- JUnit Jupiter; HTTP-проверки маршрутизации с локальными тестовыми backend-серверами.
- Flyway.
- Lombok.

Версии и набор зависимостей объявлены в build.gradle каждого приложения.
H2 Console отключена, Open Session in View отключён. Инфраструктурные
приложения не подключают JPA и H2. OpenAPI будет добавлен вместе с документацией API.

Схемы бизнес-сервисов создаются Flyway из миграций в собственных каталогах
`src/main/resources/db/migration`. Hibernate использует `ddl-auto: validate`
и проверяет соответствие сущностей схеме, JPA-тесты используют те же миграции.
Booking Service хранит пользователей, Hotel Service — отели и номера.

В Hotel Service таблица `hotels` содержит название до 200 символов и адрес
до 500 символов. Таблица `rooms` хранит ссылку на отель, номер до 32 символов,
флаг операционной доступности и счётчик `times_booked`, изначально равный 0.
Флаг доступности описывает возможность использования номера, например после
ремонта; занятость по датам будет учитываться отдельно.

Номер уникален внутри своего отеля, в разных отелях одинаковые номера допустимы.
Обязательный внешний ключ не позволяет сохранить номер без существующего отеля
или удалить отель, пока в нём остаются номера. Каскадного удаления нет.
Проверка непустых строк появится с DTO на этапе реализации API.

## Сборка

Требуются JDK 21 и доступ к репозиториям Gradle/Maven Central при первой сборке.
Глобально установленный Gradle не нужен. Из каталога любого приложения:

```sh
./gradlew build
```

В Windows используется gradlew.bat. Для запуска тестов отдельно: ./gradlew test.

## Локальный запуск

Приложения запускаются из своих каталогов, каждое в отдельном терминале.
Для бизнес-сервисов предварительно задаются ключи JWT, как описано ниже,
а для Booking Service — учётные данные начального администратора.

| Порядок | Каталог          | Команда           | Порт |
|---------|------------------|-------------------|------|
| 1       | discovery-server | ./gradlew bootRun | 8761 |
| 2       | hotel-service    | ./gradlew bootRun | 8081 |
| 3       | booking-service  | ./gradlew bootRun | 8082 |
| 4       | api-gateway      | ./gradlew bootRun | 8080 |

Eureka Dashboard: http://localhost:8761/. Регистрация и обновление клиентского
кэша выполняются асинхронно: сразу после запуска Gateway может вернуть 503.
Health каждого приложения доступен по /actuator/health, информация — /actuator/info.
В обоих бизнес-сервисах доступ к info требует токен ADMIN. Доступны только эти два
Actuator endpoint, детали health не раскрываются.

| Переменная окружения | По умолчанию                  | Назначение                                           |
|----------------------|-------------------------------|------------------------------------------------------|
| SERVER_PORT          | По таблице выше               | Порт конкретного приложения                          |
| SERVER_ADDRESS       | 127.0.0.1                     | Адрес привязки HTTP-сервера                          |
| EUREKA_URL           | http://localhost:8761/eureka/ | Адрес реестра для клиентов; завершающий / обязателен |
| SERVICE_HOSTNAME     | localhost                     | Имя, которое клиент регистрирует в Eureka            |
| DB_PASSWORD          | Пусто                         | Пароль локальной H2 бизнес-сервиса                   |

Конфигурация предназначена для локального учебного стенда. При контейнеризации
потребуется задать SERVER_ADDRESS и доступный другим контейнерам SERVICE_HOSTNAME.
Данные H2 теряются при остановке процесса; сценарий частичного восстановления
после потери одной БД не поддерживается; стенд требуется перезапустить целиком.

## Пользовательские JWT

Токен действует один час и содержит идентификатор пользователя в `sub`, роли,
issuer, audience и время выпуска. При проверке времени допускается расхождение
часов до 60 секунд. Аутентификация использует заголовок `Authorization: Bearer`.
Сессии и cookies для неё не используются.

Для запуска требуется пара RSA-ключей размером не менее 2048 бит. Пример
создания из корня репозитория с OpenSSL:

```sh
mkdir -p secrets
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out secrets/jwt-private.pem
openssl pkey -in secrets/jwt-private.pem -pubout -out secrets/jwt-public.pem
chmod 600 secrets/jwt-private.pem
```

Публичный ключ имеет формат X.509 PEM, приватный — PKCS#8 PEM без шифрования.
Каталог secrets исключён из Git. Следующие переменные задаются в окружении
Booking Service. Hotel Service использует тот же публичный ключ, приватный ключ
ему не требуется. Пути в примере вычисляются из корня репозитория:

```sh
export JWT_PUBLIC_KEY="file:$(pwd)/secrets/jwt-public.pem"
export JWT_PRIVATE_KEY="file:$(pwd)/secrets/jwt-private.pem"
```

`JWT_ISSUER` по умолчанию равен `hotel-booking`, `JWT_AUDIENCE` — `hotel-api`.
Значения issuer и audience совпадают в обоих бизнес-сервисах. При отсутствии
ключей или неверном формате соответствующий сервис не запускается. Booking Service
также проверяет совпадение публичного и приватного ключей.

Публичными остаются GET /actuator/health и POST /api/v1/users/register,
/api/v1/users/auth. Маршруты управления пользователями требуют ADMIN,
маршруты бронирований — USER. Остальные пути и методы закрыты.
Ошибки доступа возвращаются как `application/problem+json`: 401 при отсутствии
валидного токена и 403 при недостаточных правах.

## Доступ к Hotel Service

Hotel Service проверяет пользовательский JWT по публичному ключу, без обращения
к Booking Service. Правила одинаковы для прямых запросов и запросов через Gateway.

| Операции                                                        | Доступ         |
|-----------------------------------------------------------------|----------------|
| GET /api/v1/hotels и /api/v1/hotels/{id}                        | USER или ADMIN |
| GET /api/v1/rooms, /api/v1/rooms/{id} и /api/v1/rooms/recommend | USER или ADMIN |
| GET /api/v1/rooms/statistics                                    | ADMIN          |
| POST /api/v1/hotels и /api/v1/rooms                             | ADMIN          |
| PATCH и DELETE /api/v1/hotels/{id} и /api/v1/rooms/{id}         | ADMIN          |

GET /actuator/health остаётся публичным. Остальные пути и методы закрыты.
Проверка доступа уже действует, сами контроллеры отелей и номеров появятся
на следующих этапах.

## Межсервисные JWT

Для POST /api/v1/rooms/{id}/confirm-availability и /api/v1/rooms/{id}/release
предусмотрена отдельная аутентификация. Booking Service выпускает токен через
`InternalTokenService`, который будет использоваться HTTP-клиентом бронирований.
Публичного эндпоинта выдачи служебных токенов нет.

Служебный JWT подписывается тем же приватным RSA-ключом, что и пользовательский,
но содержит `sub=booking-service`, `scope=reservations:write` и отдельный audience.
Время действия — 120 секунд, допустимое расхождение часов — 60 секунд.
`SERVICE_JWT_AUDIENCE` задаётся одинаково в обоих бизнес-сервисах и по умолчанию
равен `hotel-internal`. Совпадение с `JWT_AUDIENCE` останавливает запуск.
Issuer берётся из `JWT_ISSUER`.

Пользовательские токены, включая ADMIN, получают 401 на внутренних операциях.
Корректный служебный токен без права `reservations:write` получает 403.
Служебный токен не подходит для публичного API Hotel Service и Booking Service.
Gateway не публикует внутренние пути, даже при наличии служебного токена.
Контроллеры резервирования ещё не реализованы, поэтому разрешённый внутренний
запрос пока получает 404.

## Регистрация и вход

Публичные адреса имеют вид `/api/v1/resource`, например `/api/v1/users/register`.
Такая же структура используется для совместимых маршрутов Gateway.
Actuator и Eureka сохраняют свои стандартные адреса.

Оба запроса принимают JSON с полями `username` и `password`. Username уникален
с учётом регистра и содержит от 3 до 64 латинских букв, цифр или символов `_.-`.
Пароль занимает от 12 до 72 байт в UTF-8 и используется без обрезания пробелов
или нормализации. Неизвестные поля отклоняются, роль при регистрации всегда USER.

| Метод и путь                | Ответ                                                          |
|-----------------------------|----------------------------------------------------------------|
| POST /api/v1/users/register | 201, объект `user` с id, username, role и объект `token`       |
| POST /api/v1/users/auth     | 200, объект с accessToken, tokenType: Bearer и expiresIn: 3600 |

Маршруты доступны на Gateway (порт 8080) и напрямую в Booking Service (порт 8082).
Для запросов с подготовленным JSON-файлом secrets/credentials.json:

```sh
curl http://localhost:8080/api/v1/users/register -H 'Content-Type: application/json' --data-binary @secrets/credentials.json
curl http://localhost:8080/api/v1/users/auth -H 'Content-Type: application/json' --data-binary @secrets/credentials.json
```

Неверные данные запроса возвращают 400. Ошибки в полях перечисляются в `violations`
без введённых значений. Занятый username даёт 409 с кодом `USERNAME_ALREADY_EXISTS`,
а неизвестный пользователь и неверный пароль — одинаковый ответ 401
`INVALID_CREDENTIALS`. Пароли и хеши отсутствуют в ответах.

## Начальный администратор

В Booking Service предусмотрено создание первого аккаунта ADMIN при запуске.
Инициализация включена по умолчанию, встроенных логина и пароля нет.
Параметры задаются в окружении Booking Service:

| Переменная               | По умолчанию | Назначение                               |
|--------------------------|--------------|------------------------------------------|
| BOOTSTRAP_ADMIN_ENABLED  | true         | Отключение инициализации значением false |
| BOOTSTRAP_ADMIN_USERNAME | Не задано    | Логин администратора                     |
| BOOTSTRAP_ADMIN_PASSWORD | Не задано    | Пароль администратора                    |

При включённой инициализации обязательны оба значения, даже если аккаунт уже
существует. К ним применяются те же ограничения, что при регистрации:
от 3 до 64 символов `[A-Za-z0-9_.-]` в логине и от 12 до 72 байт UTF-8 в пароле.
Отсутствующие или некорректные значения останавливают запуск, сообщение об ошибке
содержит только названия полей. При выключенной инициализации учётные данные
не проверяются и аккаунт не создаётся.

Пароль нового администратора хранится как хеш bcrypt. Если указанный логин уже
принадлежит ADMIN, аккаунт сохраняется без изменений, в том числе при другом
пароле в конфигурации. Совпадение с логином USER останавливает запуск сервиса
без повышения роли. Эта настройка предназначена для создания аккаунта, смена
пароля через неё не выполняется.

Вход администратора использует обычный POST `/api/v1/users/auth` и возвращает
JWT с ролью ADMIN. Поскольку H2 работает в памяти, после остановки приложения
аккаунт теряется и при следующем запуске создаётся заново, если инициализация включена.

## Управление пользователями

Все операции доступны только с JWT роли ADMIN, как напрямую в Booking Service,
так и через Gateway. Создание принимает `username`, `password` и обязательную
строковую роль `USER` или `ADMIN`. Ограничения логина и пароля совпадают с регистрацией.

| Метод и путь              | Ответ                         |
|---------------------------|-------------------------------|
| POST /api/v1/users        | 201, созданный пользователь   |
| GET /api/v1/users         | 200, страница пользователей   |
| GET /api/v1/users/{id}    | 200, пользователь             |
| PATCH /api/v1/users/{id}  | 200, обновлённый пользователь |
| DELETE /api/v1/users/{id} | 204, без тела                 |

Пользователь представлен полями `id`, `username`, `role`, пароли и хеши в ответы
не включаются. Список отсортирован по `id` по возрастанию. Параметр `page` начинается
с нуля, `size` принимает значения от 1 до 100, по умолчанию — 20. Ответ содержит
`content`, `page`, `size`, `totalElements`. Страница за пределами списка пуста.
Идентификатор пользователя — положительное число типа Long.

PATCH принимает любое непустое подмножество полей `username`, `password`, `role`.
Отсутствующее поле сохраняет своё значение, явный `null` и неизвестные поля
отклоняются с 400. Например, `{"role":"ADMIN"}` меняет только роль.
Новый пароль хешируется, остальные изменения не затрагивают сохранённый хеш.

Некорректные поля, идентификаторы и параметры пагинации возвращают 400.
Отсутствующий пользователь даёт 404 с кодом `USER_NOT_FOUND`, занятый username —
409 `USERNAME_ALREADY_EXISTS`. При конфликте всё изменение откатывается.
Повторное удаление уже отсутствующего пользователя возвращает 404.
Проверка истории бронирований при удалении будет добавлена вместе с моделью Booking.

JWT сохраняет выданные права до истечения срока действия. Изменение роли или пароля,
как и удаление аккаунта, не отзывает уже выпущенные токены. После входа с актуальными
учётными данными новый токен содержит текущую роль.

## Совместимые маршруты Gateway

Дополнительные адреса доступны на Gateway и преобразуются в канонические пути
Booking Service. Метод, JSON, заголовок Authorization, query-параметры и ответ
сервиса сохраняются.

| Маршрут Gateway             | Путь Booking Service   |
|-----------------------------|------------------------|
| POST /api/v1/user/register  | /api/v1/users/register |
| POST /api/v1/user/auth      | /api/v1/users/auth     |
| POST /api/v1/user           | /api/v1/users          |
| PATCH /api/v1/user?id={id}  | /api/v1/users/{id}     |
| DELETE /api/v1/user?id={id} | /api/v1/users/{id}     |

Для PATCH и DELETE обязателен один положительный `id` в query-параметрах.
Отсутствующее, повторённое, некорректное или выходящее за диапазон Long значение
возвращает 400 `INVALID_REQUEST_PARAMETERS` без обращения к Booking Service.
Неверсионированные адреса и неуказанные методы не маршрутизируются.
