# Hotel Project

REST API системы бронирования отелей. Один репозиторий содержит четыре
независимых Spring Boot приложения, каждое собирается своим Gradle Wrapper
без исходников, библиотек и корневой сборки остальных приложений.

## Состояние реализации

Реализован инфраструктурный каркас: Eureka Server,
Gateway с явными маршрутами, два бизнес-приложения с отдельными H2.
В Booking Service добавлены сущность пользователя, роли USER/ADMIN и репозиторий,
username уникален с учётом регистра, поле password предназначено для хеша пароля.
Booking Service выпускает JWT с подписью RS256 и проверяет токены на входящих
запросах. Регистрация и вход доступны через Gateway, пароли хранятся как хеши
bcrypt. Начальный администратор создаётся при включении инициализации
через внешнюю конфигурацию. Права доступа разделены между USER и ADMIN.
ADMIN может создавать, просматривать, изменять и удалять пользователей.
Оба бизнес-сервиса самостоятельно проверяют JWT. Hotel Service разграничивает
публичные запросы по ролям, а для внутренних операций принимает отдельный
служебный токен Booking Service. В Hotel Service добавлены сущности отеля и номера
с репозиториями и миграциями БД, а также журнал занятости `room_reservations`.
API отелей поддерживает создание, постраничный список, просмотр, частичное
изменение и удаление. Для номеров доступны создание,
просмотр по ID, частичное изменение и удаление. Поиск свободных номеров по датам
и рекомендации поддерживают фильтр отеля и постраничную выдачу. ADMIN доступна
статистика занятости номеров за период. Внутренние
операции резервирования и освобождения номеров доступны в Hotel Service;
Booking Service создаёт бронирования с явно указанным номером, подтверждает их
в Hotel Service и выполняет компенсацию при ошибках. USER доступны личная история,
просмотр и отмена своих бронирований. Автоматический подбор ещё не добавлен.
Фоновый обработчик
отменяет просроченные операции и повторяет незавершённое освобождение номеров.
Без токена защищённые маршруты возвращают 401.

## Стек

- Java 21, Spring Boot 4.1.1, Spring Cloud BOM 2025.1.4.
- Gradle 9.2.1, Groovy DSL, отдельный Wrapper с SHA-256 дистрибутива у каждого приложения.
- Spring Cloud Gateway Server Web MVC, Eureka, LoadBalancer.
- Spring MVC, Spring Data JPA, H2 in-memory, Bean Validation.
- Spring Security Resource Server и JWT в обоих бизнес-сервисах.
- JUnit Jupiter; HTTP-проверки маршрутизации с локальными тестовыми backend-серверами.
- Flyway.
- Lombok.

Версии и набор зависимостей объявлены в build.gradle каждого приложения.
H2 Console отключена, Open Session in View отключён. Инфраструктурные
приложения не подключают JPA и H2. OpenAPI будет добавлен вместе с документацией API.

Схемы бизнес-сервисов создаются Flyway из миграций в собственных каталогах
`src/main/resources/db/migration`. Hibernate использует `ddl-auto: validate`
и проверяет соответствие сущностей схеме, JPA-тесты используют те же миграции.
Booking Service хранит пользователей и бронирования, Hotel Service — отели,
номера и журнал занятости.

В Booking Service миграция V2 добавляет таблицу `bookings`. Каждая запись связана
с локальным пользователем, пара `(user_id, request_id)` уникальна во всех статусах.
Один UUID может использоваться разными пользователями. `room_id` и `hotel_id` —
внешние идентификаторы без связей с БД Hotel Service. Для автоматического подбора
номер может отсутствовать до выбора кандидата.

Бронирование сохраняет способ выбора номера, даты проживания, статус
`PENDING`, `CONFIRMED` или `CANCELLED`, время создания и срок завершения операции.
Даты представлены `LocalDate`, временные отметки — `Instant`.
В БД запрещён пустой или обратный интервал проживания. Новая запись получает
статус `PENDING`; версия используется для оптимистической блокировки.
Флаг `release_pending` и причина `COMPENSATION` или `USER_CANCELLATION` позволяют
хранить незавершённое освобождение номера. Изменения состояния выполняются
в коротких транзакциях с блокировкой записи бронирования, HTTP-вызовы проходят
между ними. Связь с пользователем не допускает каскадного удаления.

Миграция V3 добавляет `next_recovery_at` и индекс очереди восстановления.
Для существующих незавершённых операций время первой попытки берётся из
`deadline_at`. Завершённые бронирования в очередь не включаются.
Миграция V4 добавляет индекс личной истории по пользователю, времени создания и `id`.

В Hotel Service таблица `hotels` содержит название до 200 символов и адрес
до 500 символов. Таблица `rooms` хранит ссылку на отель, номер до 32 символов,
флаг операционной доступности и счётчик `times_booked`, изначально равный 0.
Флаг доступности описывает возможность использования номера, например после
ремонта; занятость по датам будет учитываться отдельно.

Номер уникален внутри своего отеля, в разных отелях одинаковые номера допустимы.
Обязательный внешний ключ не позволяет сохранить номер без существующего отеля
или удалить отель, пока в нём остаются номера. Каскадного удаления нет.
API отелей и номеров проверяет обязательность полей и длину строк до сохранения в БД.

Миграция V2 добавляет `room_reservations`: ссылка на номер, внешний `booking_id`,
UUID `request_id`, даты и состояние `RESERVED` или `RELEASED`. Пара
`(booking_id, room_id)` уникальна независимо от состояния. Связи с таблицами
Booking Service нет, внешний ключ ведёт только на локальный номер и запрещает
его удаление при наличии истории. Каскадное удаление записей не настроено.

Для `RESERVED` обязательны обе даты и `start_date < end_date`; интервал включает
дату начала и исключает дату окончания. Для `RELEASED` допустимо отсутствие обеих
дат: такая запись понадобится, если отмена придёт раньше подтверждения. Одна
дата без другой и пустой или обратный интервал запрещены ограничением БД.
Каждая операция подтверждения или освобождения выполняется в локальной
транзакции с блокировкой строки номера. Проверка занятости и изменение журнала и счётчика
завершаются вместе. Интервалы пересекаются, если начало каждого раньше конца
другого; соседние интервалы допустимы.

## Идентификаторы сущностей

Идентификаторы сущностей имеют тип `Long` в Java и `BIGINT` в БД. Это относится
к пользователям, отелям, номерам и бронированиям. `requestId` остаётся
UUID: он обозначает запрос для проверки идемпотентности.

Маршруты сущностей ограничены цифрами: `/{id:[0-9]+}`. Такой же шаблон используется
в Gateway. Буквы, дробная запись и знак минуса в сегменте ID не подходят маршруту
и дают 404. Нулевой ID и числовое значение за пределами `Long` дают 400.
Именованные операции, например `recommend`, объявляются отдельными маршрутами.

## Сборка

Требуются JDK 21 и доступ к репозиториям Gradle/Maven Central при первой сборке.
Глобально установленный Gradle не нужен. Из каталога любого приложения:

```sh
./gradlew build
```

В Windows используется gradlew.bat. Для запуска тестов отдельно: ./gradlew test.

## Локальный запуск

Приложения запускаются из своих каталогов, каждое в отдельном терминале.
Для бизнес-сервисов предварительно задаются ключи JWT, как описано ниже,
а для Booking Service — учётные данные начального администратора.

| Порядок | Каталог          | Команда           | Порт |
|---------|------------------|-------------------|------|
| 1       | discovery-server | ./gradlew bootRun | 8761 |
| 2       | hotel-service    | ./gradlew bootRun | 8081 |
| 3       | booking-service  | ./gradlew bootRun | 8082 |
| 4       | api-gateway      | ./gradlew bootRun | 8080 |

Eureka Dashboard: http://localhost:8761/. Регистрация и обновление клиентского
кэша выполняются асинхронно: сразу после запуска Gateway может вернуть 503.
Health каждого приложения доступен по /actuator/health, информация — /actuator/info.
В обоих бизнес-сервисах доступ к info требует токен ADMIN. Доступны только эти два
Actuator endpoint, детали health не раскрываются.

| Переменная окружения | По умолчанию                  | Назначение                                           |
|----------------------|-------------------------------|------------------------------------------------------|
| SERVER_PORT          | По таблице выше               | Порт конкретного приложения                          |
| SERVER_ADDRESS       | 127.0.0.1                     | Адрес привязки HTTP-сервера                          |
| EUREKA_URL           | http://localhost:8761/eureka/ | Адрес реестра для клиентов; завершающий / обязателен |
| SERVICE_HOSTNAME     | localhost                     | Имя, которое клиент регистрирует в Eureka            |
| DB_PASSWORD          | Пусто                         | Пароль локальной H2 бизнес-сервиса                   |

Конфигурация предназначена для локального учебного стенда. При контейнеризации
потребуется задать SERVER_ADDRESS и доступный другим контейнерам SERVICE_HOSTNAME.
Данные H2 теряются при остановке процесса; сценарий частичного восстановления
после потери одной БД не поддерживается; стенд требуется перезапустить целиком.

## Пользовательские JWT

Токен действует один час и содержит идентификатор пользователя в `sub`, роли,
issuer, audience и время выпуска. При проверке времени допускается расхождение
часов до 60 секунд. Аутентификация использует заголовок `Authorization: Bearer`.
Сессии и cookies для неё не используются.

Для запуска требуется пара RSA-ключей размером не менее 2048 бит. Пример
создания из корня репозитория с OpenSSL:

```sh
mkdir -p secrets
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out secrets/jwt-private.pem
openssl pkey -in secrets/jwt-private.pem -pubout -out secrets/jwt-public.pem
chmod 600 secrets/jwt-private.pem
```

Публичный ключ имеет формат X.509 PEM, приватный — PKCS#8 PEM без шифрования.
Каталог secrets исключён из Git. Следующие переменные задаются в окружении
Booking Service. Hotel Service использует тот же публичный ключ, приватный ключ
ему не требуется. Пути в примере вычисляются из корня репозитория:

```sh
export JWT_PUBLIC_KEY="file:$(pwd)/secrets/jwt-public.pem"
export JWT_PRIVATE_KEY="file:$(pwd)/secrets/jwt-private.pem"
```

`JWT_ISSUER` по умолчанию равен `hotel-booking`, `JWT_AUDIENCE` — `hotel-api`.
Значения issuer и audience совпадают в обоих бизнес-сервисах. При отсутствии
ключей или неверном формате соответствующий сервис не запускается. Booking Service
также проверяет совпадение публичного и приватного ключей.

Публичными остаются GET /actuator/health и POST /api/v1/users/register,
/api/v1/users/auth. Маршруты управления пользователями требуют ADMIN,
маршруты бронирований — USER. Остальные пути и методы закрыты.
Ошибки доступа возвращаются как `application/problem+json`: 401 при отсутствии
валидного токена и 403 при недостаточных правах.

## Доступ к Hotel Service

Hotel Service проверяет пользовательский JWT по публичному ключу, без обращения
к Booking Service. Правила одинаковы для прямых запросов и запросов через Gateway.

| Операции                                                        | Доступ         |
|-----------------------------------------------------------------|----------------|
| GET /api/v1/hotels и /api/v1/hotels/{id}                        | USER или ADMIN |
| GET /api/v1/rooms, /api/v1/rooms/{id} и /api/v1/rooms/recommend | USER или ADMIN |
| GET /api/v1/rooms/statistics                                    | ADMIN          |
| POST /api/v1/hotels и /api/v1/rooms                             | ADMIN          |
| PATCH и DELETE /api/v1/hotels/{id} и /api/v1/rooms/{id}         | ADMIN          |

GET /actuator/health остаётся публичным. Остальные пути и методы закрыты.
API отелей, управление номерами, поиск, рекомендации и статистика занятости
реализованы.

## Управление отелями

Маршруты доступны через Gateway и напрямую в Hotel Service по одинаковым адресам.
Чтение разрешено USER и ADMIN, создание, изменение и удаление — ADMIN.

| Метод и путь               | Ответ                 |
|----------------------------|-----------------------|
| POST /api/v1/hotels        | 201, созданный отель  |
| GET /api/v1/hotels         | 200, страница отелей  |
| GET /api/v1/hotels/{id}    | 200, отель            |
| PATCH /api/v1/hotels/{id}  | 200, изменённый отель |
| DELETE /api/v1/hotels/{id} | 204, без тела         |

Отель представлен полями `id`, `name` и `address`. Создание принимает `name`
и `address`: непустые строки длиной до 200 и 500 символов соответственно.
Строки из одних пробельных символов отклоняются, остальные значения сохраняются
без обрезания пробелов. Числа и boolean вместо строк, неизвестные поля и
некорректный JSON дают 400 с кодом `INVALID_REQUEST_BODY`.

Список принимает `page` от 0 и `size` от 1 до 100, по умолчанию 20. Ответ содержит
`content`, `page`, `size`, `totalElements`, порядок — по возрастанию id.
За пределами списка возвращается пустая страница с тем же общим количеством.

В `PATCH` пропущенное поле остаётся прежним. Явный `null` даёт 400
`INVALID_REQUEST_BODY`, пустой объект и нарушения ограничений строк — 400
`VALIDATION_FAILED`. Такой же код используется для неверных значений page,
size и нулевого id. Переполнение числового ID и неверный тип query-параметра
дают 400 `INVALID_REQUEST_PARAMETERS`.

Отсутствующий отель возвращает 404 `HOTEL_NOT_FOUND`. Если в отеле есть номера,
удаление возвращает 409 `HOTEL_HAS_ROOMS`, отель и номера сохраняются.
После удаления последнего номера отель можно удалить, повторное удаление
отсутствующего отеля возвращает 404.

## Управление номерами

Номера создаются в существующем отеле. Прямые запросы в Hotel Service и запросы
через Gateway используют одинаковые пути и правила доступа.

| Метод и путь              | Доступ         | Ответ                 |
|---------------------------|----------------|-----------------------|
| POST /api/v1/rooms        | ADMIN          | 201, созданный номер  |
| GET /api/v1/rooms/{id}    | USER или ADMIN | 200, номер            |
| PATCH /api/v1/rooms/{id}  | ADMIN          | 200, изменённый номер |
| DELETE /api/v1/rooms/{id} | ADMIN          | 204, без тела         |

Создание принимает `hotelId`, `number` и `available`. Идентификатор отеля —
положительное целое JSON-число, номер — непустая строка до 32 символов,
`available` — boolean. Пробелы внутри и по краям номера сохраняются, строка
из одних пробельных символов отклоняется. Преобразование строк и чисел
в другие типы не выполняется.

Ответ содержит `id`, `hotelId`, `number`, `available` и `timesBooked`.
Счётчик начинается с 0, в запросах его задавать нельзя. `PATCH` принимает только
`number` и `available`: пропущенное поле сохраняется, явный `null`, неизвестное
поле и неверный тип дают 400 `INVALID_REQUEST_BODY`. Пустой объект, пустой номер
или превышение длины дают 400 `VALIDATION_FAILED`. Изменение `hotelId` не поддерживается.

Одинаковые номера в одном отеле дают 409 `ROOM_NUMBER_ALREADY_EXISTS`, в разных
отелях они допустимы. Конфликт при изменении откатывает весь запрос, включая
изменение доступности. Отсутствующий отель при создании даёт 404 `HOTEL_NOT_FOUND`,
отсутствующий номер — 404 `ROOM_NOT_FOUND`. Удаление номера сохраняет сам отель,
повторное удаление возвращает 404.

Поиск по датам и рекомендации доступны через GET `/api/v1/rooms` и
`/api/v1/rooms/recommend`, статистика — через GET `/api/v1/rooms/statistics`.
Удаление номера с любой историей резервирования даёт 409 `ROOM_HAS_RESERVATIONS`, включая записи
`RELEASED` без дат. Отключение номера при действующем текущем или будущем
резервировании даёт 409 `ROOM_HAS_FUTURE_RESERVATIONS`: проверяется `RESERVED`
с датой окончания позже текущей даты UTC. Завершившееся сегодня или освобождённое
резервирование отключению не мешает; номер комнаты менять можно. Проверки и
изменения используют ту же блокировку, что внутренние операции, поэтому
изменение остальных полей при конфликте также откатывается.

## Поиск номеров и рекомендации

Оба запроса доступны USER и ADMIN, напрямую в Hotel Service и через Gateway:

```http
GET /api/v1/rooms?startDate=2027-01-11&endDate=2027-01-13&hotelId=1&page=0&size=20
GET /api/v1/rooms/recommend?startDate=2027-01-11&endDate=2027-01-13&hotelId=1&page=0&size=20
```

`startDate` и `endDate` обязательны, передаются датами `YYYY-MM-DD` без времени
и задают интервал с исключённым концом. Начало строго раньше окончания;
прошедшие интервалы также допустимы. Необязательный положительный `hotelId`
ограничивает выборку отелем. Без него поиск охватывает все отели, а фильтр по
несуществующему отелю возвращает пустую страницу.

В выдачу входят только номера с `available=true`, для которых нет пересекающихся
резервирований `RESERVED`. Соседние интервалы и записи `RELEASED`, включая записи
без дат, поиску не мешают. Обычный список отсортирован по `id` по возрастанию;
рекомендации — по `timesBooked`, затем по `id`. Номера с меньшим историческим
числом бронирований оказываются раньше, без статистических моделей.

Ответ имеет поля `{content, page, size, totalElements}`, элементы `content`
совпадают с ответом просмотра номера. `page` начинается с 0, `size` — от 1 до 100,
по умолчанию 20. `totalElements` учитывает всю отфильтрованную выборку. Страница
за её пределами пустая, общее количество при этом сохраняется.

Пропущенные даты и неверные типы параметров дают 400 `INVALID_REQUEST_PARAMETERS`.
Нарушение порядка дат, диапазона страницы, размера или ID отеля даёт
400 `VALIDATION_FAILED`. Поиск не меняет журнал и счётчики, найденный номер
не резервируется: подтверждение заново проверяет занятость под блокировкой.

## Статистика занятости

GET `/api/v1/rooms/statistics` доступен только ADMIN, напрямую в Hotel Service
и через Gateway. Например:

```http
GET /api/v1/rooms/statistics?startDate=2027-01-10&endDate=2027-01-20&hotelId=1&page=0&size=20
```

Обязательные даты, необязательный `hotelId` и пагинация используют те же правила,
что поиск номеров. В отчёт входят все номера выбранного отеля, включая
недоступные и не имеющие резервирований. Без фильтра учитываются все отели,
при неизвестном отеле возвращается пустая страница. Порядок — по `roomId`
по возрастанию. Ответ содержит `{content, page, size, totalElements}`.

Каждый элемент `content` имеет поля `roomId`, `timesBooked`, `bookedNights`,
`totalNights` и `occupancyRate`. `totalNights` — длительность запрошенного
интервала, его конец не включён. В `bookedNights` суммируются только пересечения
записей `RESERVED` с этим периодом: часть резервирования за пределами отчёта
не учитывается, соседние интервалы и записи `RELEASED` дают нулевой вклад.

`occupancyRate` — доля занятых ночей от 0 до 1: четыре ночи из десяти дают `0.4`.
При отсутствии занятости `bookedNights` и `occupancyRate` равны нулю. `timesBooked` остаётся накопленным
историческим счётчиком номера, поэтому не ограничивается периодом отчёта.
Суммирование выполняется в БД; чтение статистики не меняет журнал и счётчики.

## Межсервисные JWT

Для POST /api/v1/rooms/{id}/confirm-availability и /api/v1/rooms/{id}/release
предусмотрена отдельная аутентификация. Booking Service выпускает токен через
`InternalTokenService`, который используется HTTP-клиентом бронирований.
Публичного эндпоинта выдачи служебных токенов нет.

Служебный JWT подписывается тем же приватным RSA-ключом, что и пользовательский,
но содержит `sub=booking-service`, `scope=reservations:write` и отдельный audience.
Время действия — 120 секунд, допустимое расхождение часов — 60 секунд.
`SERVICE_JWT_AUDIENCE` задаётся одинаково в обоих бизнес-сервисах и по умолчанию
равен `hotel-internal`. Совпадение с `JWT_AUDIENCE` останавливает запуск.
Issuer берётся из `JWT_ISSUER`.

Пользовательские токены, включая ADMIN, получают 401 на внутренних операциях.
Корректный служебный токен без права `reservations:write` получает 403.
Служебный токен не подходит для публичного API Hotel Service и Booking Service.
Gateway не публикует внутренние пути, даже при наличии служебного токена.

Внутренние операции принимают JSON и возвращают 200 с
`{bookingId, roomId, state}`, где состояние равно `RESERVED` или `RELEASED`:

| Метод и путь                                 | Поля запроса                             |
|----------------------------------------------|------------------------------------------|
| POST /api/v1/rooms/{id}/confirm-availability | bookingId, requestId, startDate, endDate |
| POST /api/v1/rooms/{id}/release              | bookingId, requestId, reason             |

Все поля обязательны. `bookingId` — положительное целое число типа Long,
`requestId` — UUID, даты — строки ISO `YYYY-MM-DD` с `startDate < endDate`.
Причина освобождения — строка `COMPENSATION` или `USER_CANCELLATION`.
Неизвестные поля, числовые enum и подмена типов отклоняются. Ошибки формы JSON
дают 400 `INVALID_REQUEST_BODY`, нарушения обязательности, диапазона ID или
порядка дат — 400 `VALIDATION_FAILED`. Отсутствующий номер даёт 404 `ROOM_NOT_FOUND`.
Проверка начала относительно сегодняшней даты будет выполняться при создании
бронирования в Booking Service; внутренний протокол допускает отложенные повторы.

Повторное подтверждение с теми же идентификаторами и датами возвращает прежний
результат без изменения счётчика. Другой `requestId` для пары бронирование/номер
или другие даты уже принятого `RESERVED` дают 409 `IDEMPOTENCY_CONFLICT`.
Занятый или операционно недоступный номер даёт 409 `ROOM_UNAVAILABLE`.
Подтверждение после освобождения даёт 409 `RESERVATION_RELEASED` независимо от
наличия дат в освобождённой записи. При проверке сначала сверяется `requestId`.

При новом подтверждении `timesBooked` увеличивается один раз. `COMPENSATION`
освобождает интервал и уменьшает счётчик один раз; `USER_CANCELLATION` сохраняет
исторический счётчик. Освобождение без предшествующего подтверждения создаёт
`RELEASED` без дат и не меняет счётчик. Состояние `RELEASED` окончательное:
повторное освобождение ничего не меняет, в том числе при другой причине.

Подтверждение, освобождение, изменение и удаление номера используют блокировку
`PESSIMISTIC_WRITE`. Ожидание ограничено двумя секундами; при конфликте блокировки
возвращается 503 `ROOM_BUSY` без внутренних сведений БД. Hotel Service и Gateway
не повторяют эти операции автоматически. Гарантии относятся к сохранённому
состоянию одной H2, ограничения её жизненного цикла остаются прежними.

## Создание бронирования

`POST /api/v1/bookings` доступен с ролью USER через Gateway и напрямую в Booking
Service. ADMIN без роли USER не получает доступ. Пользователь определяется по JWT,
поле `userId` в JSON не допускается.

```json
{
  "requestId": "ec9429e7-e8c1-40c2-b260-63626ee33428",
  "autoSelect": false,
  "roomId": 42,
  "startDate": "2027-01-10",
  "endDate": "2027-01-12"
}
```

Сейчас поддерживается явный выбор: обязательны UUID `requestId`,
`autoSelect=false`, положительный целочисленный `roomId` и обе даты.
`hotelId` не передаётся. Автоматический подбор с `autoSelect=true` пока возвращает
400 `VALIDATION_FAILED`. Неизвестные поля, строковые числа и логические значения,
дробные ID, массивы и время вместо календарной даты отклоняются.
Для нового запроса начало не предшествует текущей дате UTC, конец строго позже
начала. Пример использует конкретные даты, которые при необходимости заменяются
на актуальный период.

Booking Service сначала сохраняет `PENDING`, затем обращается напрямую к
Hotel Service через Eureka и Spring Cloud LoadBalancer со служебным JWT.
Успешное резервирование переводит запись в `CONFIRMED`, ответ — 201.
Тело содержит `id`, `requestId`, `roomId`, `startDate`, `endDate`, `status`,
`createdAt` и `releasePending`. Заголовок `Location` указывает
`/api/v1/bookings/{id}`. Получение по этому адресу доступно владельцу бронирования.

Повтор того же запроса возвращает сохранённую запись с 200, а пока первая
операция выполняется — `PENDING` с 202 и `Location`. Нового резервирования нет.
Проверка уже принятого запроса выполняется до проверки дат относительно сегодняшнего
дня, поэтому повтор после окончания периода остаётся допустимым. Другие параметры
под тем же UUID дают 409 `IDEMPOTENCY_CONFLICT`. UUID ограничен пользователем,
разные пользователи могут применять одинаковое значение.

При ошибке бронирование становится `CANCELLED` с задачей освобождения номера.
Освобождение с причиной `COMPENSATION` выполняется и при потерянном ответе
подтверждения, поскольку удалённое резервирование могло завершиться.
Успех освобождения снимает `releasePending`; ответ `ROOM_NOT_FOUND` также
завершает задачу, поскольку отсутствующий номер не может иметь журнал резервирований.
Повтор отменённого запроса возвращает ту же запись и не запускает создание заново.

Занятый номер даёт 409 `ROOM_UNAVAILABLE`, отсутствующий — 404 `ROOM_NOT_FOUND`.
Сбой зависимости возвращает 503 `HOTEL_SERVICE_UNAVAILABLE`, таймаут HTTP-клиента
или исчерпание бюджета — 504 `BOOKING_TIMEOUT`. Если отмена опередила подтверждение, возвращается
409 `BOOKING_CANCELLED`. Ошибка сохранения состояния даёт 503
`BOOKING_STORAGE_UNAVAILABLE`. Ошибки после создания записи содержат `bookingId`
и `releasePending`, внутренние ответы и диагностические сообщения не раскрываются.

Параметры Booking Service задаются в миллисекундах:

| Переменная                   | По умолчанию | Назначение                                       |
|------------------------------|--------------|--------------------------------------------------|
| HOTEL_CONNECT_TIMEOUT_MS     | 1000         | Таймаут соединения, от 1 до 60000                |
| HOTEL_READ_TIMEOUT_MS        | 2000         | Таймаут получения ответа, от 1 до 60000          |
| HOTEL_MAX_ATTEMPTS           | 3            | Число попыток каждого confirm/release, от 1 до 5 |
| HOTEL_BACKOFF_MS             | 100          | Начальная пауза повторов, от 1 до 1000           |
| BOOKING_OPERATION_TIMEOUT_MS | 10000        | Срок операции, от 1 до 120000                    |

Пауза растёт экспоненциально с разбросом от половины до полного значения,
максимум — 1000 мс. Повторяются сетевые ошибки, таймауты и ответы 502/503/504.
Другие ответы не повторяются как временные сбои. Срок операции ограничивает
HTTP-попытки и паузы, включая компенсацию, и проверяется перед сохранением
`CONFIRMED`. Gateway и LoadBalancer не добавляют повторов записи, перенаправления
HTTP-клиент не выполняет.

Если освобождение не удалось или бюджет времени закончился, в БД остаётся
`CANCELLED` с `releasePending=true`. При недоступной БД может остаться `PENDING`.
Повтор POST показывает сохранённое состояние, а фоновый обработчик завершает
отмену и освобождение номера.

## История бронирований

Чтение доступно с ролью USER через Gateway и напрямую в Booking Service.
Владелец определяется по JWT, ADMIN без роли USER получает 403.

| Метод и путь              | Ответ                        |
|---------------------------|------------------------------|
| GET /api/v1/bookings      | 200, страница личной истории |
| GET /api/v1/bookings/{id} | 200, своё бронирование       |

История включает `PENDING`, `CONFIRMED` и `CANCELLED`, сначала идут более новые
записи по `createdAt`, при одинаковом времени — меньший `id`. Параметры `page`
и `size` задают страницу с нуля и размер от 1 до 100, по умолчанию — 20.
Например, `GET /api/v1/bookings?page=0&size=20`. Ответ содержит `content`, `page`,
`size`, `totalElements`, причём общее количество относится только к текущему
пользователю. Пустая история и страница за пределами списка возвращаются с 200.

Бронирование имеет тот же формат, что и ответ создания. Поле `releasePending`
показывает текущее состояние освобождения номера. До выбора номера `roomId`
может быть `null`. Данные читаются из БД Booking Service, поэтому просмотр
доступен и при недоступном Hotel Service.

Чужое и отсутствующее бронирование возвращают одинаковый 404
`BOOKING_NOT_FOUND` с сообщением `Booking not found`. Некорректные параметры
пагинации дают 400. Для `id` действуют общие правила числовых маршрутов.

## Отмена бронирования

`DELETE /api/v1/bookings/{id}` доступен владельцу с ролью USER. Запись остаётся
в личной истории со статусом `CANCELLED`. Ответ содержит тот же объект,
что и просмотр по ID, а `Location` указывает канонический адрес бронирования.

При завершённом освобождении или отсутствии выбранного номера возвращается
200 с `releasePending=false`. Если освобождение ещё требуется, ответ — 202
с `releasePending=true`. Текущее состояние доступно через GET по `Location`.
Повторный DELETE возвращает текущее состояние, сохраняя первоначальную причину
отмены и время фоновой попытки. Повторное освобождение выполняет фоновый обработчик.

При отмене `PENDING` сохраняется причина `COMPENSATION`: незавершённое создание
может быть отменено, даже если подтверждение Hotel Service ещё выполняется.
Если резервирование уже произошло, компенсация уменьшает счётчик номера один раз.
Для `CONFIRMED` используется `USER_CANCELLATION`, которая освобождает даты
и сохраняет исторический `timesBooked`.

Статус и причина выбираются под блокировкой записи Booking Service.
Если подтверждение опередило отмену, сохраняется `USER_CANCELLATION`.
Если первой завершилась отмена, поздний ответ подтверждения оставляет
бронирование в `CANCELLED`. Hotel Service обрабатывает повторные освобождения
идемпотентно с исходными `bookingId` и `requestId`.

После сохранения отмены освобождение выполняется вне транзакции. Для него
выделяется новое окно `BOOKING_OPERATION_TIMEOUT_MS`, независимо от срока
исходного создания. После этого окна задача доступна фоновому обработчику.
Ошибка Hotel Service или сохранения подтверждения освобождения оставляет 202
и задачу в БД. Если не удалось сохранить саму отмену, возвращается 503
`BOOKING_STORAGE_UNAVAILABLE`.

Чужое и отсутствующее бронирование возвращают одинаковый 404 `BOOKING_NOT_FOUND`.
Для некорректного `id` действуют общие правила числовых маршрутов, ADMIN без
роли USER получает 403.

## Фоновое восстановление бронирований

Обработчик включён по умолчанию. Он выбирает задачи по времени следующей попытки
и `id`, ограничивая размер порции. Просроченный `PENDING` становится `CANCELLED`
с причиной `COMPENSATION`. Если номер ещё не выбран, освобождение не требуется.
Подтверждённые бронирования не отменяются по таймеру.

Перед HTTP-вызовом запись блокируется, её состояние проверяется повторно,
а время следующей попытки сохраняется в БД. Поэтому второй обработчик не захватит
ту же задачу, пока действует окно текущей попытки. Блокировка снимается до
обращения к Hotel Service. Причина освобождения сохраняется при повторах, в том
числе `USER_CANCELLATION` для пользовательской отмены.

Успешный `release` снимает `releasePending` и убирает задачу из очереди.
При ошибке она остаётся в БД и снова становится доступной после срока попытки
и паузы повтора. Ошибка одной записи не останавливает обработку остальных.
Ни перезапуск обработчика, ни потеря ответа освобождения не создают новое
бронирование: используется прежняя пара `bookingId`/`requestId`, а повторное
освобождение идемпотентно в Hotel Service. Запоздалая ошибка старого обработчика
не возвращает уже завершённую задачу в очередь.

| Переменная                        | По умолчанию | Назначение                                                             |
|-----------------------------------|--------------|------------------------------------------------------------------------|
| BOOKING_RECOVERY_ENABLED          | true         | Включение фонового обработчика                                         |
| BOOKING_RECOVERY_BATCH_SIZE       | 20           | Размер порции, от 1 до 100                                             |
| BOOKING_RECOVERY_POLL_INTERVAL_MS | 5000         | Пауза после цикла и перед первым запуском, от 1 до 3600000 мс          |
| BOOKING_RECOVERY_RETRY_DELAY_MS   | 5000         | Пауза после срока попытки перед повторным захватом, от 1 до 3600000 мс |
| BOOKING_RECOVERY_CYCLE_TIMEOUT_MS | 10000        | Бюджет цикла, от 1 до 120000 мс                                        |

Один цикл выполняется последовательно в управляемом Spring потоке. Срок
HTTP-попытки ограничен оставшимся бюджетом цикла и `BOOKING_OPERATION_TIMEOUT_MS`.
Повторы внутри вызова выполняет `HotelServiceGateway` по настройкам `HOTEL_*`.
Проверка бюджета между записями не прерывает уже начатую транзакцию;
ожидание блокировки записи ограничено двумя секундами.

При сохранённой БД обработчик продолжает работу после перезапуска, включая
задачи с истёкшим окном захвата. Это проверяется на файловой H2. Стандартный
локальный стенд использует H2 in-memory и теряет данные при остановке процесса,
поэтому восстановление после потери БД по-прежнему не поддерживается.

## Регистрация и вход

Публичные адреса имеют вид `/api/v1/resource`, например `/api/v1/users/register`.
Такая же структура используется для совместимых маршрутов Gateway.
Actuator и Eureka сохраняют свои стандартные адреса.

Оба запроса принимают JSON с полями `username` и `password`. Username уникален
с учётом регистра и содержит от 3 до 64 латинских букв, цифр или символов `_.-`.
Пароль занимает от 12 до 72 байт в UTF-8 и используется без обрезания пробелов
или нормализации. Неизвестные поля отклоняются, роль при регистрации всегда USER.

| Метод и путь                | Ответ                                                          |
|-----------------------------|----------------------------------------------------------------|
| POST /api/v1/users/register | 201, объект `user` с id, username, role и объект `token`       |
| POST /api/v1/users/auth     | 200, объект с accessToken, tokenType: Bearer и expiresIn: 3600 |

Маршруты доступны на Gateway (порт 8080) и напрямую в Booking Service (порт 8082).
Для запросов с подготовленным JSON-файлом secrets/credentials.json:

```sh
curl http://localhost:8080/api/v1/users/register -H 'Content-Type: application/json' --data-binary @secrets/credentials.json
curl http://localhost:8080/api/v1/users/auth -H 'Content-Type: application/json' --data-binary @secrets/credentials.json
```

Неверные данные запроса возвращают 400. Ошибки в полях перечисляются в `violations`
без введённых значений. Занятый username даёт 409 с кодом `USERNAME_ALREADY_EXISTS`,
а неизвестный пользователь и неверный пароль — одинаковый ответ 401
`INVALID_CREDENTIALS`. Пароли и хеши отсутствуют в ответах.

## Начальный администратор

В Booking Service предусмотрено создание первого аккаунта ADMIN при запуске.
Инициализация включена по умолчанию, встроенных логина и пароля нет.
Параметры задаются в окружении Booking Service:

| Переменная               | По умолчанию | Назначение                               |
|--------------------------|--------------|------------------------------------------|
| BOOTSTRAP_ADMIN_ENABLED  | true         | Отключение инициализации значением false |
| BOOTSTRAP_ADMIN_USERNAME | Не задано    | Логин администратора                     |
| BOOTSTRAP_ADMIN_PASSWORD | Не задано    | Пароль администратора                    |

При включённой инициализации обязательны оба значения, даже если аккаунт уже
существует. К ним применяются те же ограничения, что при регистрации:
от 3 до 64 символов `[A-Za-z0-9_.-]` в логине и от 12 до 72 байт UTF-8 в пароле.
Отсутствующие или некорректные значения останавливают запуск, сообщение об ошибке
содержит только названия полей. При выключенной инициализации учётные данные
не проверяются и аккаунт не создаётся.

Пароль нового администратора хранится как хеш bcrypt. Если указанный логин уже
принадлежит ADMIN, аккаунт сохраняется без изменений, в том числе при другом
пароле в конфигурации. Совпадение с логином USER останавливает запуск сервиса
без повышения роли. Эта настройка предназначена для создания аккаунта, смена
пароля через неё не выполняется.

Вход администратора использует обычный POST `/api/v1/users/auth` и возвращает
JWT с ролью ADMIN. Поскольку H2 работает в памяти, после остановки приложения
аккаунт теряется и при следующем запуске создаётся заново, если инициализация включена.

## Управление пользователями

Все операции доступны только с JWT роли ADMIN, как напрямую в Booking Service,
так и через Gateway. Создание принимает `username`, `password` и обязательную
строковую роль `USER` или `ADMIN`. Ограничения логина и пароля совпадают с регистрацией.

| Метод и путь              | Ответ                         |
|---------------------------|-------------------------------|
| POST /api/v1/users        | 201, созданный пользователь   |
| GET /api/v1/users         | 200, страница пользователей   |
| GET /api/v1/users/{id}    | 200, пользователь             |
| PATCH /api/v1/users/{id}  | 200, обновлённый пользователь |
| DELETE /api/v1/users/{id} | 204, без тела                 |

Пользователь представлен полями `id`, `username`, `role`, пароли и хеши в ответы
не включаются. Список отсортирован по `id` по возрастанию. Параметр `page` начинается
с нуля, `size` принимает значения от 1 до 100, по умолчанию — 20. Ответ содержит
`content`, `page`, `size`, `totalElements`. Страница за пределами списка пуста.
Идентификатор пользователя — положительное число типа Long.

PATCH принимает любое непустое подмножество полей `username`, `password`, `role`.
Отсутствующее поле сохраняет своё значение, явный `null` и неизвестные поля
отклоняются с 400. Например, `{"role":"ADMIN"}` меняет только роль.
Новый пароль хешируется, остальные изменения не затрагивают сохранённый хеш.

Некорректные поля и параметры пагинации возвращают 400. Для ID действуют
общие правила числовых маршрутов, описанные выше.
Отсутствующий пользователь даёт 404 с кодом `USER_NOT_FOUND`, занятый username —
409 `USERNAME_ALREADY_EXISTS`. При конфликте всё изменение откатывается.
Повторное удаление уже отсутствующего пользователя возвращает 404.
При наличии хотя бы одного бронирования в любом статусе удаление возвращает
409 `USER_HAS_BOOKINGS`, пользователь и его история сохраняются. Внешний ключ
защищает историю, если бронирование появилось после предварительной проверки.

JWT сохраняет выданные права до истечения срока действия. Изменение роли или пароля,
как и удаление аккаунта, не отзывает уже выпущенные токены. После входа с актуальными
учётными данными новый токен содержит текущую роль.

## Совместимые маршруты Gateway

Дополнительные адреса доступны на Gateway и преобразуются в канонические пути
Booking Service. Метод, JSON, заголовок Authorization, query-параметры и ответ
сервиса сохраняются.

| Маршрут Gateway             | Путь Booking Service   |
|-----------------------------|------------------------|
| POST /api/v1/user/register  | /api/v1/users/register |
| POST /api/v1/user/auth      | /api/v1/users/auth     |
| POST /api/v1/user           | /api/v1/users          |
| PATCH /api/v1/user?id={id}  | /api/v1/users/{id}     |
| DELETE /api/v1/user?id={id} | /api/v1/users/{id}     |
| POST /api/v1/booking        | /api/v1/bookings       |
| GET /api/v1/booking/{id}    | /api/v1/bookings/{id}  |
| DELETE /api/v1/booking/{id} | /api/v1/bookings/{id}  |

Для PATCH и DELETE алиаса `/api/v1/user` обязателен один положительный `id` в query-параметрах.
Отсутствующее, повторённое, некорректное или выходящее за диапазон Long значение
возвращает 400 `INVALID_REQUEST_PARAMETERS` без обращения к Booking Service.
Неверсионированные адреса и неуказанные методы не маршрутизируются.
